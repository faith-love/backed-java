# 并发与线程安全：先决定为什么并发

这组专题回答四个问题：**为什么要开线程、怎么创建和收回线程、共享数据怎么保护、多个任务怎么协作**。代码以 Java 11 为基线，适用于理解当前项目的 Spring Boot 2.7 服务；Java 21 的虚拟线程只做版本说明。

前端可以把“提交后台任务再取结果”类比 `Promise`，但 Java 中不同任务可能真的在不同 CPU 核心同时执行。`async`、`Future` 和 Promise 都不自动保证业务安全，也不保证操作已经持久化成功。

## 并发、并行、同步和异步分别是什么

| 词语 | 含义 | 例子 |
|---|---|---|
| 并发 | 一段时间内多个任务都在推进，可能交替执行 | 单核 CPU 在多个请求之间切换 |
| 并行 | 同一时刻多个任务真正同时执行 | 多核 CPU 同时计算两份报表 |
| 同步 | 调用者按调用结果继续流程 | Controller 等数据库返回再组装响应 |
| 异步 | 提交后先返回结果句柄/接收状态，稍后完成 | 提交导出任务，页面凭任务 ID 查询进度 |
| 阻塞 | 当前线程等待条件，暂时不能继续执行 | `Future.get()` 等待结果、阻塞 JDBC 调用 |

异步不等于不使用线程，也不等于实现中完全不阻塞；把阻塞 I/O 放进线程池，只是把等待转移到工作线程。同步/异步描述调用流程，阻塞/非阻塞描述线程的等待行为。

## Web 服务已经有线程，是否还要自己创建

常见 Servlet 服务由 Tomcat 等容器的线程池处理请求。两个用户同时点击按钮，Controller 和同一个 Spring Service 对象可能已被两个线程同时调用。即使代码中没有 `new Thread`，也需要考虑共享字段安全。

例如，把当前用户放在单例 Service 的 `currentUser` 字段里，会让请求 A 写入的用户被请求 B 覆盖。把用户作为方法参数传递通常更直接；方法局部引用指向的对象若仍来自共享缓存，也并不会自动线程安全。

Spring Cloud Gateway 常使用响应式事件循环，其线程模型与 Servlet 不同。在事件循环里阻塞数据库或等待锁会拖住许多请求。先确定模块使用哪种运行时，再决定框架调度方式。

## 什么情况下值得增加并发

| 场景 | 建议 | 解决的问题与代价 |
|---|---|---|
| 页面同时需要互不依赖的用户信息和订单统计 | 有界池并发查询，两项完成再返回 | 延迟有机会接近较慢查询；增加下游并发，需要超时 |
| CPU 密集计算可独立切分 | 实测后用接近可用 CPU 容量的计算池 | 利用多核；过多线程增加切换 |
| 超长导出、账单生成 | 持久化任务，后台执行，前端查进度 | 避免 HTTP 长等待；处理重启、重试和状态 |
| 支付后的邮件、积分、报表更新 | 支付状态与 outbox 一起提交，消费者异步处理 | 核心确认不等慢任务；消费者需幂等 |
| 同一订单的创建、付款、发货有依赖 | 保持状态机顺序，不能随意并行 | 避免未支付就发货 |
| 普通列表只执行一条 SQL | 通常沿用已有请求线程 | 另开线程再立即 get 只增加开销 |
| 数据库连接池已耗尽 | 先限流、优化和排队 | 加线程只让更多任务等连接 |

线程需要线程栈、调度开销、对象和上下文，还会占用数据库/HTTP 连接。I/O 等待比例高时可能允许较多线程，但必须受下游容量和总流量约束。

## 共享数据为什么会算错

`count++` 需要读取旧值、加一、写回。A、B 同时读到 0 时，都计算得到 1，最终可能只有 1。

```text
线程 A                 线程 B
读取 count = 0         读取 count = 0
计算 0 + 1             计算 0 + 1
写回 count = 1         写回 count = 1

期望完成两次累加，实际丢失一次更新。
```

这叫竞态条件：结果取决于无法固定的执行交错。测试偶尔没复现不证明安全；断点和日志改变调度后，还可能让问题暂时消失。

## 原子性、可见性、有序性与 happens-before

- **原子性**：操作不能被按同一协议访问的其他线程观察到部分完成。原子加一不等于“检查余额再扣款”整组操作原子。
- **可见性**：A 改值后 B 如何可靠观察更新。普通字段缺少同步约定时，不保证 B 在需要的时刻看到更新。
- **有序性**：编译器和 CPU 可以合法重排。跨线程依赖应通过内存模型建立，不能只凭源码顺序推断。

**happens-before** 描述可见性和顺序保证，不是“墙上时钟先发生”。常见规则：

| 规则 | 实际用途 |
|---|---|
| 同一 monitor 解锁 happens-before 后续加锁 | 相同锁保护的读写 |
| 同一 volatile 写 happens-before 后续读 | 状态标志、发布已初始化的不可变快照 |
| `Thread.start()` 前的操作 happens-before 新线程操作 | 启动前准备输入 |
| 线程结束 happens-before 成功等待结束的 `join()` 返回 | 确认计算完成后读结果；限时 join 若未等到结束不能套用 |
| 提交任务前的操作 happens-before 任务执行；任务完成 happens-before 成功 `Future.get()` 后的操作 | 池任务输入交付与结果获取 |

锁外读取字段、把不同锁当成同一把锁、初始化未完成就发布 `this`，都会破坏这类约定。

## volatile、原子类、锁分别管什么

| 手段 | 解决什么问题 | 不解决什么 |
|---|---|---|
| 不可变对象、任务局部数据 | 尽量消除共享写入 | 引用的其他可变对象仍可能共享 |
| `volatile` | 可见性及相关顺序保证 | 不把 `count++` 变成原子操作 |
| `AtomicInteger`/`AtomicReference` | 单个值的原子操作/CAS | 不自动维护多个变量共同的不变量 |
| `LongAdder` | 高竞争统计累加 | 并发写入时 sum 非原子快照，不适合支付额度/唯一序号 |
| `synchronized`/`Lock` | 临界区互斥，保护多个字段关系 | 不覆盖其他进程或数据库 |
| 数据库条件更新/事务/唯一约束 | 多应用实例共同维护持久状态 | 不自动覆盖远程支付平台 |

例如库存扣减可用数据库条件更新：仅当现有库存足够才减库存，再检查影响行数。单机锁只能保护当前实例中的代码，不能代替数据库约束。

## 协作工具不是同一种锁

| 工具 | 适用场景 | 生命周期/要点 |
|---|---|---|
| `CountDownLatch` | 等多个准备动作完成、测试起跑门 | 到 0 后不能重置；失败路径也要释放等待者 |
| `CyclicBarrier` | 多个参与者每轮到齐再前进 | 可复用；超时/中断可破坏屏障 |
| `Phaser` | 分阶段任务且参与者动态增减 | 需正确登记与注销 |
| `Semaphore` | 最多允许 N 个操作并行调用下游 | 仅成功取得许可后在 finally 释放；不是按每秒次数限流 |
| `BlockingQueue` | 生产者与消费者传递任务 | 明确容量和满队列行为 |
| `Condition`/`wait` | 等状态条件成立，再由修改方唤醒 | 按规则持锁调用，并循环复查条件，应对虚假唤醒 |

## ThreadLocal：线程隔离不等于任务自动传递

`ThreadLocal` 把值关联到当前线程，适合同一调用链中的 trace 等上下文。它不会克隆可变对象，也不会让值自动从请求线程传到工作线程。

线程池复用线程，未清理的值可能串到下一项任务。`InheritableThreadLocal` 也不解决复用问题：继承发生在线程创建时，而不是每次任务提交时。

```java
// 片段：每次任务显式建立并清理上下文；业务输入仍优先通过方法参数传递。
private static final ThreadLocal<String> TRACE_ID = new ThreadLocal<>();

// 在工作线程执行这段包装，临时设定本任务的 traceId。
static void runWithTrace(String traceId, Runnable action) {
    // 保存外层值，支持嵌套调用。
    String previous = TRACE_ID.get();
    try {
        // 当前线程的后续调用可读到本次上下文。
        TRACE_ID.set(traceId);
        // 异常继续抛出，不吞掉业务失败。
        action.run();
    } finally {
        // 无论成功失败，都恢复外层值或移除引用。
        if (previous == null) {
            TRACE_ID.remove();
        } else {
            TRACE_ID.set(previous);
        }
    }
}
```

Spring 事务上下文通常绑定线程。传递用户 ID 或 traceId 不会让原请求的数据库事务跨线程延续；异步任务需有自己的事务边界。`@Async` 的用法见[线程池专题](./thread-pools.md)。

## 支付场景：哪些并发必须设计清楚

连点支付、平台重试通知、主动查单发现成功，都可能并发更新同一个订单：

1. 前端 loading 减少误操作，服务端仍要处理重复请求。
2. 下单幂等键让同一业务意图复用支付尝试。
3. 通知先验签，再核对商户、渠道、订单、金额、币种和状态。
4. 数据库事务与条件更新只允许合法状态转换，防止重复发货。
5. 事务内记录 outbox，事务外投递，消费者幂等处理。
6. 网络超时表示结果未知，查单确认后再决定处理，不能直接重复扣款。

具体代码见[支付宝与微信支付示例](../../examples/online-payment.md)。本机模拟用于学习并发；真实支付需要官方 SDK、商户配置及持久存储。

## 排查线程问题

1. 记录任务提交、开始执行、完成三个时间点，区分排队慢与执行慢。
2. 查看活跃线程、队列长度、拒绝次数、失败率与下游连接等待。
3. 用 `jcmd <pid> Thread.print` 获取线程快照，替换成实际进程号；检查锁、Future 和连接等待。
4. 对比 CPU、堆和下游指标，线程增加但吞吐不变时寻找其他瓶颈。
5. 检查池内任务再次提交到同一池并等待，是否所有线程都被父任务占住。
6. 检查取消/失败时锁、许可、连接和 ThreadLocal 是否释放。

线程快照只反映一个时刻。`WAITING` 可能是正常空闲；`BLOCKED` 特指等待 monitor，Lock 等待不一定表现为该状态。

## 练习

- 选一个页面接口，区分独立可并行和必须顺序执行的步骤。
- 为任务设计总超时、异常和取消策略，解释取消是否等于下游已停止。
- 在两个实例处理支付回调的前提下，解释为什么 `synchronized` 不够。
- 修改示例队列容量，观察拒绝行为，设计前端错误反馈。
- 从当前项目搜索线程池 Bean 和共享字段，用源码和日志验证实际使用方式。
