# 锁、原子操作与业务一致性（Java 11）

锁解决的是：**多个线程共同使用一份可变数据时，怎样让一段必须整体成立的操作不被其他线程穿插破坏。** 例如“先检查库存，再扣减库存”包含两个动作；只把其中一次读或写变成线程安全，仍可能超卖。

对前端开发者来说，可以从“用户连续点两次提交”理解需求，但不要把禁用按钮当成并发控制。请求可能来自不同浏览器、重试、消息队列和多个服务实例。Java 本地锁、数据库事务和支付幂等分别覆盖不同范围，需要先认清共享数据在哪里。

本章按“要保护什么 → 用什么机制 → 能保证到哪里”展开。先学习[线程与任务](./threads.md)，再把锁与[线程池](./thread-pools.md)中的取消、超时和资源关闭放在一起理解。

## 先找不变量，再确定临界区

**解决的问题：** 防止只对语法加锁，却没有保护真正的业务规则。

不变量是操作完成后必须始终成立的关系。例如：

- 本地库存：`remaining >= 0`，并且 `remaining + sold == initialStock`。
- 缓存配置：版本号和对应配置必须来自同一次更新。
- 转账账本：在数据库事务范围内，扣款和入账必须整体成功或整体回滚。

临界区是访问这些共享状态时必须受同一同步协议保护的代码。正确性取决于**所有相关读写**是否遵守协议，而不只是写方法上有没有 `synchronized`。

~~~java
// 错误示意：即使 get/set 各自线程安全，两步之间也可能插入其他请求。
if (stock.get() > 0) {
    stock.decrementAndGet(); // 多个线程可能先后扣到负数。
}
~~~

如果只保护一个数字，可以使用带条件的 CAS 重试；如果同时保护库存、销量和本地预留记录，使用同一把锁通常更容易表达规则。若状态在数据库，应该由数据库条件更新和事务保证这些规则，见本章的[库存与支付](#库存与支付-业务正确性在哪里兜底)。

## 锁的分类是不同维度

**解决的问题：** 避免把“可重入锁、乐观锁、读写锁”误当成相互排斥的同一级类别。一个实现可能同时属于多个分类。

| 分类维度 | 含义 | 例子与取舍 |
|---|---|---|
| 悲观 / 乐观 | 先获取排他访问权，或先读取并在提交时检查冲突 | `synchronized`、数据库行锁属于悲观控制；版本号更新、CAS、`StampedLock` 乐观读取采用乐观检查 |
| 独占 / 共享 | 同一时刻只允许一个持有者，或允许符合规则的多个持有者 | `ReentrantLock` 独占；读写锁的读锁共享、写锁独占；共享不代表允许写 |
| 公平 / 非公平 | 获取时是否倾向等待队列中较早的请求 | 公平锁减少插队和饥饿风险，通常降低吞吐；不承诺操作系统调度顺序 |
| 可重入 / 不可重入 | 同一线程已经持锁时，能否再次获取同一把锁 | `synchronized`、`ReentrantLock` 可重入；`StampedLock` 不可重入 |
| 阻塞 / 自旋 | 获取失败后挂起等待，或继续尝试 | 自旋消耗 CPU；阻塞有调度成本；实际实现可能混合使用，不能只凭 API 名字断言 |
| 本地 / 数据库 / 分布式 | 协调范围在哪里 | JVM 对象锁协调同一进程；数据库协调访问同一数据库的数据；分布式协调依赖外部系统 |

乐观方案适合冲突较少且重试成本可控的场景；冲突很多时，持续失败重试会浪费资源。悲观方案更直接，但临界区过长会让其他请求排队。分类没有“越高级越快”的排序。

## synchronized：默认先掌握的本地互斥方式

### 它解决什么问题

`synchronized` 为关联对象的 monitor 提供互斥，并建立线程间的内存可见性。适合**短小、只操作本地共享状态、不需要等锁超时或中断取消**的临界区。

优点是语法直接，正常返回或抛异常都会自动解锁；缺点是等待获取 monitor 时没有 `tryLock` 或超时 API，线程中断也不会让它自动退出等锁。

### 对象锁与类锁：关键是锁对象的身份

| 写法 | 实际使用的锁 | 谁会竞争 |
|---|---|---|
| 实例方法 `synchronized void update()` | 当前实例 `this` | 调用同一实例同步方法、或同步同一实例的线程 |
| `synchronized (mutex) { ... }` | 表达式引用的对象 | 使用同一个 `mutex` 对象的线程 |
| 静态方法 `static synchronized void update()` | 声明类的 `Class` 对象 | 使用该 `Class` 对象的线程 |
| `synchronized (Settings.class) { ... }` | `Settings` 的 `Class` 对象 | 同一个类加载器中该类的类锁使用者 |

两个 `new Service()` 对象的实例锁不同，互不阻塞。实例锁与类锁也不同；不能用实例锁保护一个被所有实例共享的 `static` 计数器，却误以为类之间已经互斥。

推荐使用 `private final Object mutex = new Object()` 表达私有锁。`final` 防止中途换锁；`private` 降低外部代码意外占用它的风险。不要锁定字符串字面量、装箱缓存对象或每次调用新建的对象；它们可能意外共享，或者根本没有共享。

### monitor 与 happens-before：为什么读者也要遵守锁协议

对象 monitor 可以理解为 JVM 维护的进入许可：同一时间只有一个线程持有它。`synchronized` 代码块通常由字节码的 `monitorenter/monitorexit` 表达；同步方法由同步标记交给 JVM 管理。

Java 内存模型规定：**对某个 monitor 的解锁，happens-before 后续对同一个 monitor 的成功加锁。** 因此，前一个持有者在解锁前完成的写入，对后一个正确加锁的读取者可见。

这不是“释放任何锁都会刷新所有线程”的承诺。如果写线程锁 `mutexA`、读线程锁 `mutexB`，或读线程完全不锁，就不能据此建立同一个同步边界。对已发布的不可变快照可以另行设计无锁读取，但需要明确安全发布方式。

### 可重入：同一线程再次进入不会把自己挡住

一个同步方法可以调用同一对象的另一个同步方法。当前线程已经持有 monitor，会增加重入计数；退出时逐层减少，最后一层退出才真正释放。

可重入解决了“带锁的方法组合调用”的问题，**不解决多个锁之间的循环等待**。线程甲持有 A 再等 B，线程乙持有 B 再等 A，仍会死锁。

## ReentrantLock：需要控制等待时使用

### 它比 synchronized 多解决什么问题

`ReentrantLock` 同样提供互斥、可重入和内存可见性，但允许主动决定“等多久、能否取消、没拿到锁怎么办”，还支持多个 `Condition` 等待队列。

| API | 获取失败时的行为 | 适用场景 |
|---|---|---|
| `lock()` | 等待直到成功；获取过程不会因中断抛出异常 | 确定要等待完成的短临界区 |
| `tryLock()` | 立即返回 `false` | 定时刷新已在运行时跳过本次触发 |
| `tryLock(timeout, unit)` | 最多等待给定时长，可被中断 | 请求有延迟预算，忙时返回可识别的状态 |
| `lockInterruptibly()` | 等待时可响应中断并抛 `InterruptedException` | 任务取消后应尽快离开等待队列 |
| `unlock()` | 当前持有线程释放一层持有计数 | 必须放进取得锁之后的 `finally` |

**超时边界：** `tryLock(100, MILLISECONDS)` 只限制等锁时间。拿到锁后在里面调用慢接口，整个方法仍可能运行数秒。完整请求超时还要覆盖网络、数据库及后续计算。

### 获取成功之后才进入 try/finally

~~~java
// 方法需要声明 throws InterruptedException，或在适当边界处理取消。
lock.lockInterruptibly(); // 获取失败并抛中断异常时，没有持有锁。
try {
    updateLocalState(); // 只执行需要这把锁保护的操作。
} finally {
    lock.unlock(); // 与一次成功获取对应，不能遗漏或多释放。
}
~~~

这是方法内片段，`lock` 和 `updateLocalState()` 由所在业务类定义。不要把获取语句放进一个无条件 `unlock()` 的 `try` 内部，否则获取被中断后仍会尝试释放未持有的锁，抛出 `IllegalMonitorStateException`。

`lockInterruptibly()` 只是让**等待锁**可取消；取得锁后执行的业务仍要自己响应中断。处理 `InterruptedException` 时，可以继续向调用方传播，或在不能继续抛出的边界恢复中断标记并停止当前任务，不能吞掉异常继续执行。

### 公平性：减少插队也有成本

`new ReentrantLock()` 默认非公平；`new ReentrantLock(true)` 倾向让等待较久的线程先获取锁，通常吞吐更低。公平性不是严格的请求先来先服务，也不保证某线程在操作系统中及时得到 CPU。

还有一个容易漏掉的区别：**不带超时的 `tryLock()` 即使面对公平锁，也允许直接尝试取得空闲锁，不遵守公平排队策略。** 带超时的版本会遵守该锁的公平策略。

先测量是否存在长期饥饿、等待时长严重不均，再决定是否需要公平锁；不要因为名字听起来正确就默认开启。

## ReadWriteLock：让多个只读任务同时访问

### 解决的问题与使用条件

普通互斥锁让两个互不修改数据的读取也排队。`ReentrantReadWriteLock` 将访问分为读锁和写锁：

- 多个线程可以同时持有读锁。
- 写锁独占；有其他线程持读锁或写锁时，写者要等待。
- 写者持锁期间，其他线程不能读取受保护的状态。

它适合读多写少、每次读取确有一定工作量的本地索引、配置和字典缓存。若只是读一个不可变对象引用，`volatile` 发布快照通常更简单；若临界区极短或写入频繁，维护读写锁的成本可能抵消收益。

“读多”不自动等于“读写锁更快”。需要结合读取耗时、写入延迟、锁竞争和是否能使用不可变快照进行测量。默认非公平模式在持续竞争下可能让某一方等待很久；公平模式也会带来吞吐成本。

### 所有读写必须服从同一套协议

读取用该读写锁的读锁，修改用**同一个读写锁对象**的写锁。返回内部可变 `Map` 会破坏协议：调用方可以在解锁后修改它，或遍历正在变化的数据。

解决方式是在持读锁时复制数据，再返回不可变快照。`Collections.unmodifiableMap(original)` 只是只读视图，原始 `Map` 后续变化仍会被看见；需要先复制。如果值本身是可变对象，还要深拷贝或使用不可变值类型。

### 升级风险与降级方式

**读锁升级成写锁：不能直接做。** 当前线程持读锁时再请求写锁，会被自己的读锁以及其他读者阻塞，可能永远拿不到写锁。

安全的思路是：释放读锁 → 获取写锁 → **重新检查业务条件** → 执行更新。重新检查不可省略，因为两把锁之间的空档可能有其他写者更新数据。

`ReentrantReadWriteLock` 支持写锁降级：持有写锁时先获取读锁，再释放写锁，随后在读锁保护下继续读取。先释放写锁再获取读锁会产生竞争窗口。降级适合更新后需要继续读取一致结果的少数场景，必须让每一次获取都对应释放。

## StampedLock：乐观读取必须验证

### 解决的问题

`StampedLock` 在 Java 8 引入，Java 11 可用。它提供写锁、读锁和乐观读取，适合**读取非常频繁、写入很少、状态能安全地复制到局部变量**的场景。

乐观读取避免每次都登记一个真正的读锁：取得 stamp → 复制字段 → `validate(stamp)` → 成功才使用副本；验证失败则获取读锁并重新读取。验证的意思是“复制期间没有成功取得过写锁破坏这次读取的有效性”，并不保证返回以后数据永远不变。

下面是可放进单独类文件的实现片段，所有写操作也必须使用该 `StampedLock` 的写锁：

~~~java
import java.util.concurrent.locks.StampedLock;

/** 用两个基本类型字段演示可验证的乐观快照。 */
final class Position {
    private final StampedLock lock = new StampedLock();
    private double x;
    private double y;

    /** 同一写锁保证两个坐标整体更新。 */
    void move(double nextX, double nextY) {
        long stamp = lock.writeLock();
        try {
            x = nextX;
            y = nextY;
        } finally {
            lock.unlockWrite(stamp);
        }
    }

    /** 返回独立数组，不把内部可变对象暴露给调用方。 */
    double[] snapshot() {
        long stamp = lock.tryOptimisticRead();
        // 先复制到局部变量，这时不能把读到的值用于外部副作用。
        double currentX = x;
        double currentY = y;
        if (!lock.validate(stamp)) {
            // 写入可能穿插发生，必须在真正的读锁下重新读取。
            stamp = lock.readLock();
            try {
                currentX = x;
                currentY = y;
            } finally {
                lock.unlockRead(stamp);
            }
        }
        // 验证通过后只使用局部副本，不能又回头读取共享字段。
        return new double[] {currentX, currentY};
    }
}
~~~

### 代价与限制

- **不可重入：** 持有写锁时调用另一个再次获取同一锁的方法，可能卡住自己；嵌套调用和回调尤其要小心。
- **乐观读取不是互斥：** 期间可能看到不一致状态，不可先扣款、发送事件、访问越界数组，再指望验证失败能撤销副作用。
- **不能任意遍历可变结构：** 乐观遍历同时修改的 `HashMap` 等结构可能在验证前就发生异常或其他问题。复杂结构优先采用真正的读锁或不可变快照。
- **stamp 需要正确配对：** 根据实际持有模式调用对应释放方法；乐观 stamp 本身不是持有的读锁，不能直接当读锁释放。
- **锁转换可能失败：** `tryConvertToWriteLock(stamp)` 返回 `0` 表示失败。不能拿着失败结果继续修改；要按原持有模式释放、重新获取并重新检查条件。
- **不提供与 `ReentrantLock` 一样的可重入、所有权及 `Condition` 使用模型：** 它是更低层的工具，不是默认替代品。

只有通过测量确认锁竞争影响性能、且团队能维护这些约束时，再考虑使用它。

## volatile、CAS、Atomic 与 LongAdder：它们不都是锁

### volatile：发布状态，不把多步操作变成原子

**解决的问题：** 某线程修改标志或替换配置引用，其他线程需要按内存模型的规定看到该变化。

对同一个 `volatile` 字段的写，happens-before 后续对该字段的读；它也约束相关操作的重排。适合停止标志、状态发布、替换一个已经构造完成的不可变快照引用。

`volatile int count` 的 `count++` 仍是读、加、写三个步骤；`volatile Map` 只让引用的发布有保障，不让 `Map` 内部操作自动线程安全。它不能单独维持多个字段的整体关系。

### CAS：有条件地替换一个值

**解决的问题：** 只有当前值仍等于我刚才读取的旧值时才提交更新，避免覆盖其他线程的修改。

`compareAndSet(expected, updated)` 把比较和写入作为一次原子操作。失败表示值已不符合预期；调用方可以重新读取并按业务规则有限重试，或返回冲突。`AtomicInteger`、`AtomicLong`、`AtomicReference` 提供这些原子更新 API，底层可能使用 CAS 或其他平台原子指令。

~~~java
// 方法内片段：stock 是共享的 AtomicInteger，初始值非负。
for (int attempt = 0; attempt < 20; attempt++) {
    int current = stock.get(); // 读取本轮期望值。
    if (current <= 0) {
        return false; // 当前没有可售库存。
    }
    if (stock.compareAndSet(current, current - 1)) {
        return true; // 条件判断与本次扣减在 CAS 提交点整体成立。
    }
    // 有竞争者修改过库存，下轮读取最新值后重新判断。
}
return false; // 达到本地重试上限；真实 API 应区分忙碌与售罄。
~~~

这仍只是单 JVM、单变量的方案。把库存和订单记录分别放进两个 `Atomic` 对象，不能让二者一起提交或回滚。重试函数中也不能调用支付、发消息等不可重复副作用；例如 `updateAndGet` 的函数可能被重复执行。

**ABA 问题：** 一个引用从 A 变成 B 又变回 A，普通 CAS 只检查当前值相等，可能察觉不到中间变化。如果业务必须识别这段历史，需要版本号，或在合适场景使用 `AtomicStampedReference`；不是每个简单计数器都需要处理 ABA。

### AtomicLong 与 LongAdder 怎么选

| 需求 | 更合适的选择 | 原因 |
|---|---|---|
| 生成单 JVM 内精确的递增序号 | `AtomicLong.incrementAndGet()` | 每次返回原子递增后的结果；跨 JVM 唯一 ID 另行设计 |
| 检查并扣减一个本地数量 | `AtomicInteger` CAS，或锁 | 检查与更新必须整体提交 |
| 高竞争的请求量、命中量统计 | `LongAdder` | 将更新压力分散到多个内部单元，通常以更多内存换吞吐 |
| 读取时必须是一个原子瞬时值 | `AtomicLong` | `LongAdder.sum()` 在并发更新时不是原子快照 |
| 多字段事务关系 | 同一把锁，或对应存储层事务 | 多个原子字段不等于整体原子 |

`LongAdder` 适合指标，不适合用 `sum()` 判断“还剩一个名额”然后扣减；并发 `sumThenReset()` 也不能作为精确结算的时间窗口边界。停止所有写入后再读取总数，与写入进行中的读取有不同语义。

## Condition、Semaphore、CountDownLatch 各解决什么问题

它们与并发控制有关，但不能都叫互斥锁。

| 工具 | 解决的问题 | 关键规则与业务例子 |
|---|---|---|
| `Condition` | 等待“队列非空、队列未满”等状态变化 | 来自 `Lock.newCondition()`；在持对应锁时检查条件、`await`、`signal`；生产者消费者通常优先用 `BlockingQueue` |
| `Semaphore` | 控制同时使用资源的任务数量 | 例如同时最多 5 个本地导出任务；许可允许跨线程释放，不具备互斥锁的线程所有权约束 |
| `CountDownLatch` | 等待若干事件完成 | 一次性门闩；初始化完成后开放服务、主线程等待任务完成；不能自动重置，也不保护共享字段的每次读写 |

### Condition：等待时释放锁，醒来后重新检查

`await()` 会释放关联的锁，并在返回前重新取得它；因此其他线程才有机会改变条件。必须使用 `while (!conditionSatisfied)` 循环检查，因为可能出现虚假唤醒，或者另一个线程先消耗了资源。

`signal()` 只是通知等待者有机会重新竞争锁，不会马上把锁交给它，也不保证对应条件在它最终取得锁时仍成立。等待应考虑超时和中断。经典的 `Object.wait/notify` 基于 monitor 也有类似规则，而且必须在持有该 monitor 时调用。

`ReentrantReadWriteLock` 的写锁支持 `Condition`，读锁不支持。不要为了等待业务完成而在持有另一把无关锁时调用 `await()`；它只释放关联的那把锁。

### Semaphore：成功取得许可后才能释放

当 `tryAcquire(timeout, unit)` 返回 `false` 或等待被中断时，没有取得许可，不能无条件 `release()`。错误释放会凭空增加许可，让并发限制失效。即使初始许可为 1，它也不等同于可重入且有所有权的互斥锁。

单实例信号量限制的是本地同时执行数量，**不是每秒请求速率**；部署四个实例、每个实例允许五个任务，总并发可能达到二十。全局限流和资源配额需要额外设计。

### Latch：完成信号有可见性，但不是状态锁

工作线程在 `countDown()` 之前的动作，happens-before 另一个线程成功从对应 `await()` 返回后的动作。这让主线程能在任务完成后读取结果；但不使多个工作线程之间的 `count++` 变成原子。

等待应设置上限，失败路径也要安排完成信号或异常传播。前面的示例用 latch 协调开始，用带超时的 `Future.get` 观察任务结果和异常，两者作用不同。

## 死锁、饥饿与活锁

### 死锁：彼此持有对方需要的资源

**业务例子：** 本地账户转账时，线程甲先锁账户 A 再锁 B，线程乙先锁 B 再锁 A，两者都等不到第二把锁。

最直接的预防是**整个系统采用一致获取顺序**：例如按不可变且唯一的账户 ID 从小到大加锁；同一账户先处理为特殊情况。所有代码路径都要遵守，不能只有一个接口按顺序获取。

不要用可能冲突的 `hashCode` 当作天然唯一的锁顺序。如果需要细粒度锁注册表，必须保证同一业务键始终获得同一个有效锁；在持锁者或等待者还存在时随意删除条目，会产生两把锁同时保护同一个键的错误。

其他预防方式包括缩小持锁时间、避免持锁回调未知代码、避免在持锁期间等待依赖同一资源的任务。用 `tryLock` 获取多把锁时，只要任一步失败，就释放已取得的所有锁，并使用有限重试；超时本身不会自动替你释放其他锁。

### 饥饿：一直等不到机会

非公平竞争、某些长时间持锁操作或不合理线程优先级，都可能让部分任务等待很久。先观测等待分布和持锁耗时，再决定是否减少临界区、分片、限并发或启用公平模式。

### 活锁：一直活动但没有进展

多个线程同时发现冲突、同时撤销、立即再次冲突，可能消耗 CPU 却无法完成工作。重试上限、随机退避和明确的仲裁规则能缓解。随机退避用于冲突恢复，不应该用 `sleep` 猜测正确的执行先后顺序。

## 库存与支付：业务正确性在哪里兜底

### 三层控制范围不同

| 层次 | 能协调的范围 | 不能自动解决的问题 |
|---|---|---|
| Java 本地锁 | 同一 JVM 中使用同一个锁对象的线程 | 其他实例、脚本直连数据库、进程重启后的去重 |
| 数据库条件更新、约束和事务 | 对同一数据库数据的并发操作 | 外部支付服务与本地事务一起原子提交 |
| 分布式锁 | 按协议访问同一协调服务的参与者 | 锁过期后的旧持有者继续写、绕过协议的写入、业务幂等 |

`synchronized` 支付方法最多避免本进程的部分并发重入；另一实例依旧可以同时发起付款。即使只部署一个实例，进程重启后也会丢失内存中的“已处理”记录。

### 库存扣减：条件更新比先查再改更可靠

**解决的问题：** 两个服务实例都查到库存为 1，然后各自把库存扣减一次。

常见做法是在数据库执行条件更新，并判断受影响行数。下面以支持事务的关系数据库为示意，假设 `inventory.sku_id` 是主键或唯一键，参数语法由 ORM 或驱动适配：

~~~sql
-- 请求数量必须为正；在更新语句中同时检查库存是否足够。
UPDATE inventory
SET quantity = quantity - :amount
WHERE sku_id = :sku_id
  AND :amount > 0
  AND quantity >= :amount;

-- 应用必须读取受影响行数：1 表示本次条件更新成功。
-- 0 可能表示商品不存在、数量非法或库存不足，按业务契约区分。
~~~

这条语句解决并发超卖，**不解决重复请求重复扣减**。同一个订单网络重试两次，只要库存够，更新仍可能成功两次。

因此还要为业务动作建立稳定幂等键，例如库存预留表对 `(order_id, sku_id)` 设置唯一约束；在同一个数据库事务中“写入预留记录 → 条件扣减 → 保存结果”。插入重复时读取已存在的处理结果；库存不足时回滚整个事务，不能留下假成功记录。多商品订单要明确整体回滚规则，并按一致 SKU 顺序操作，降低数据库死锁概率。

数据库死锁仍可能因索引、其他事务等因素发生；应对**已明确回滚的完整事务**做有限重试，并保留幂等性。不要把某条 SQL 成功重试当成整个业务都已经恢复。

### 版本号更新：检测过期编辑

**解决的问题：** 用户甲打开库存配置页后，用户乙已经保存了新值；甲再次保存会覆盖乙的修改。

~~~sql
-- 页面提交其读取时的 expected_version；成功后版本递增。
UPDATE inventory_config
SET warning_threshold = :threshold,
    version = version + 1
WHERE sku_id = :sku_id
  AND version = :expected_version;

-- 受影响行数为 0 时不能直接当成成功，应处理不存在或版本冲突。
~~~

这就是常见的数据库乐观并发控制。前端通常应提示数据已变化，并刷新或合并；不要在未确认用户意图时，自动用最新版本号反复覆盖。

### 重复支付：唯一约束、状态机与支付方幂等一起工作

**解决的问题：** 点击重试、请求超时、服务重启或回调重复，可能让同一业务支付多次执行。

一个可靠流程至少需要下面这些规则：

1. **建立持久化的支付意图。** 为同一业务动作使用稳定幂等键并设置唯一约束；若规则是一张订单只有一个逻辑支付意图，还要对业务订单标识建立对应约束，不能让换一个请求键就绕过去。重复键携带不同金额或收款对象时要拒绝冲突。
2. **用条件更新推进状态。** 例如只允许从 `CREATED` 进入 `PROCESSING`，并检查更新行数；重复请求查询既有结果。长期停在处理中需要超时恢复及对账，不能永久丢弃重试。
3. **调用支付方时继续使用稳定幂等标识。** 本地事务不能与远程扣款自动原子提交。网络超时可能代表“支付成功但响应丢失”，此时应查询支付方或安全重试同一幂等请求。
4. **回调也要幂等。** 验证回调真实性、订单、金额和币种，为支付流水号设置唯一约束，只执行一次允许的状态迁移。
5. **处理跨系统的不确定状态。** 可结合事务内写出站事件（outbox）、可重试投递、查询与对账，让进程在任意一步崩溃后仍能恢复。outbox 本身不会让外部副作用自动恰好一次，接收方仍需幂等。

不要在持有 Java 锁或长时间数据库行锁时等待支付 HTTP 响应。缩短本地事务，并通过持久化状态协调后续流程，更容易处理超时和恢复。

### 分布式锁：协调手段不能代替数据约束

分布式锁适合限制跨实例重复调度或减少并发冲突，但租期可能到期、续约可能失败，旧持有者仍可能继续运行。需要唯一持有者令牌及安全释放协议；严格要求排除过期写入时，还需要由最终资源校验递增的 fencing token 等机制。

因此支付唯一性、库存非负等关键不变量，仍应尽量由最终数据存储的约束和条件更新兜底。不要因为“加了 Redis 锁”就删掉数据库唯一约束。

## 如何选择与排查

| 当前问题 | 先考虑的方案 |
|---|---|
| 没有共享可变数据 | 不加锁，保留局部变量或不可变对象 |
| 简短的本地多字段更新 | `synchronized` |
| 等锁需要超时、取消或多个条件队列 | `ReentrantLock` |
| 本地读多写少、读操作有一定成本 | 测量后使用读写锁，或不可变快照 |
| 极高频的简单读取且愿意维护验证逻辑 | 测量后考虑 `StampedLock` |
| 单变量原子计数/更新 | `AtomicInteger`、`AtomicLong` 或 CAS |
| 高竞争统计指标 | `LongAdder`，接受并发读取语义 |
| 限制同时执行任务数量 | `Semaphore` 或有界线程池 |
| 多实例修改库存、订单 | 数据库事务、条件更新和唯一约束 |

排查时先回答：共享对象是谁、哪些线程能访问、所有路径是否用同一把锁、返回值是否泄漏可变引用、等待是否有上限、异常是否释放资源、重试是否幂等。

在 Java 11 中，可以用 `jcmd <pid> Thread.print` 或 `jstack <pid>` 获取线程转储。monitor 竞争常见 `BLOCKED`；使用 `LockSupport` 等待的 `ReentrantLock` 等工具常显示 `WAITING` 或 `TIMED_WAITING`。不要只看到“没有 BLOCKED”就认为没有锁等待。结合等待的锁、持有者及完整调用栈定位；一次转储只能说明当时状态，必要时对比多次转储及指标。
