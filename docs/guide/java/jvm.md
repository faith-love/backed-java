# JVM 与垃圾回收

JVM 解决 Java 字节码如何运行、对象内存如何管理、线程如何调度的问题。业务开发不必一开始掌握所有 GC 算法，但要能把“请求变慢、进程内存增长、服务 OOM”映射到可观察的运行时现象。

## JVM 负责什么

Java 源码先编译成字节码，JVM 加载类、执行字节码并管理运行时内存。相同字节码可由不同平台的 JVM 执行；实际行为仍取决于 JDK 版本、启动参数和容器资源限制。

## 运行时区域：对象和线程数据放在哪里

### 解决什么问题

知道对象、局部变量和类元数据分别由哪个运行时区域承载，能缩小 OOM、栈溢出和进程内存增长的调查范围，避免把所有内存异常都当成“堆不够”。

| 区域 | 主要内容 | 典型问题 |
|---|---|---|
| 堆 | 大多数对象实例和数组 | 堆占用高、频繁 GC、OutOfMemoryError: Java heap space |
| Java 栈 | 每个线程的方法调用帧和局部变量 | 递归过深导致 StackOverflowError；线程太多消耗栈内存 |
| 元空间 | 类元数据等信息 | 动态生成大量类或类加载器无法释放时元空间增长 |
| 直接内存 | 部分 I/O 和网络库申请的堆外缓冲区 | 堆看起来不高，但进程仍可能因本地内存不足失败 |

每个线程有自己的 Java 栈；多个线程通常共享堆对象。静态字段和缓存可能让对象长期可达，从而不能被 GC 回收。

## 垃圾回收：按可达性回收

### 解决什么问题

GC 自动回收程序已经无法访问的对象，降低开发者手动管理对象内存的负担；理解可达性可以解释为什么某些“业务上已无用”的对象仍持续占用内存。

GC 通常从一组 GC Roots 出发，查找仍可达对象，并回收不可达对象。常见根包括活动线程栈引用、静态字段和 JNI 引用。

业务上需要理解：

- 短命对象很多时，年轻代回收会频繁发生。
- 长期存活对象进入老年代后，回收可能代价更高。
- 停顿时间、吞吐和内存占用之间存在权衡。
- GC 不能回收仍被程序引用但业务上已经无用的对象；这就是 Java 中常见的“逻辑内存泄漏”。

## 完整示例：静态集合如何留住对象

~~~java
import java.util.ArrayList;
import java.util.List;

/**
 * 演示对象仍被静态集合引用时，GC 不能回收它。
 * 此示例刻意展示风险，不要把无界静态集合用作真实缓存。
 */
public class RetainedObjectDemo {

    // static 字段跟随类存活；集合里的对象因此保持可达。
    private static final List<byte[]> RETAINED_DATA = new ArrayList<>();

    /**
     * 程序入口。
     *
     * @param args 命令行参数，本例不使用
     */
    public static void main(String[] args) {
        // 以小块数据说明引用关系，不通过大内存申请制造 OOM。
        byte[] sample = new byte[1024];

        // 添加后，静态集合持有 sample 的引用。
        RETAINED_DATA.add(sample);

        // 将局部变量设为 null 不会删除集合中的引用。
        sample = null;

        // 只要 RETAINED_DATA 还保存该元素，GC 就不能回收这个数组。
        System.out.println("集合仍然持有对象：" + RETAINED_DATA.size());

        // 清空集合会释放该引用；真正回收由 JVM 在合适时机决定。
        RETAINED_DATA.clear();

        // 调用 System.gc 只是建议，不保证立即执行，也不应用作常规修复。
        System.gc();

        // 生产代码应设计有界缓存、过期策略和可观测的清理机制。
        System.out.println("已移除示例中的静态引用");
    }
}
~~~

## 内存问题的常见表现

| 表现 | 可能方向 |
|---|---|
| 接口延迟周期性升高 | GC 停顿、线程池排队、数据库或外部 I/O 等待 |
| 堆使用持续上升且回收后基线不降 | 静态集合、缓存不淘汰、监听器/线程未释放、类加载器引用 |
| 进程 RSS 增长但堆占用不高 | 直接内存、线程栈、JIT、共享库或容器记账 |
| Java heap space | 堆对象无法分配，检查保留对象和峰值流量 |
| Metaspace OOM | 类元数据增加，检查动态类生成和类加载器生命周期 |
| unable to create native thread | 线程数量或操作系统资源达到限制 |

## 项目阅读与排错用途

当前项目的 bin/startup.sh 中写有 JVM 堆和 GC 参数，包括 -Xms、-Xmx、G1 相关参数、OOM heap dump 和 GC 日志路径。它说明部署脚本可以指定运行参数；不能证明所有环境都执行同一脚本或使用同一组参数。

排查线上 JVM 时先获取进程和运行时证据：

~~~bash
# 查看 Java 进程及 PID。
jcmd -l

# 查看堆概况；需要与目标 Java 进程使用相同操作系统用户。
jcmd <pid> GC.heap_info

# 查看线程栈，帮助判断线程是否阻塞在数据库、锁或外部调用。
jcmd <pid> Thread.print

# 查看 GC 利用率趋势；pid 替换为实际进程号。
jstat -gcutil <pid> 1000 10

# 导出堆转储可能带有用户数据和业务对象，需先确认安全存放位置。
jcmd <pid> GC.heap_dump /safe/path/heap.hprof
~~~

容器环境还要一起看容器内存限额、JDK 对容器的识别和实际启动参数。不要只根据本地 IDE 的 Xmx 判断线上表现。

## 排查实操：区分 CPU 忙、线程等待和内存保留

先把异常现象分成几类，避免上来就增大堆或重启：

| 现象 | 第一批证据 | 重点判断 |
|---|---|---|
| CPU 长时间偏高 | 操作系统线程级 CPU、间隔数秒的多份线程转储 | 是否同一线程持续运行同一段业务代码；是否出现热点循环或高频序列化 |
| 请求等待但 CPU 不高 | 多份线程转储、线程池/连接池指标、下游耗时 | `BLOCKED` 锁竞争、数据库连接池排队、Socket I/O 等待还是线程池队列积压 |
| 堆用量高且 GC 后基线逐渐升高 | GC 日志、对象直方图、必要时堆转储 | 缓存/集合持续持有对象，还是流量与缓存预热造成的正常波动 |
| RSS 上升但堆稳定 | 容器/进程内存、线程数、直接内存、Native Memory Tracking | 是否由线程栈、NIO 堆外缓冲、JIT 或本地库造成 |

### 1. 先确认进程、JDK 和实际参数

~~~bash
# 列出当前用户可见的 Java 进程；必要时使用服务进程所属的系统账号。
jcmd -l

# 查看目标 JVM 的实际参数，不要只看部署文档或本机 IDE 配置。
jcmd <pid> VM.flags

# 查看堆概况；它不能代替进程 RSS 或容器总内存指标。
jcmd <pid> GC.heap_info

# 查看 GC 区域使用趋势；示例每秒采样一次，共采 10 次。
jstat -gcutil <pid> 1000 10
~~~

确认命令连接的是目标 PID 和同一台机器中的正确 JDK。容器场景先进入正确容器/进程命名空间；宿主机 PID、容器 PID 和资源限额可能不同。

### 2. CPU 高时对照 OS 线程与 Java 栈

~~~bash
# 按线程显示进程 CPU，记录持续占用最高的 OS 线程 ID（TID）。
top -H -p <pid>

# 把十进制 TID 转成十六进制，供线程转储中的 nid 字段搜索。
printf '%x\n' <tid>

# 导出带锁信息的线程转储；对同一进程间隔数秒再采集一份做比较。
jcmd <pid> Thread.print -l > /safe/path/threads-1.txt
jcmd <pid> Thread.print -l > /safe/path/threads-2.txt
~~~

如果高 CPU 的 TID 在多份转储中映射到同一个 Java `nid`，且栈顶持续停留在同一段计算代码，可进一步检查循环、数据规模、正则表达式、序列化和锁竞争。单份线程转储只能说明采样瞬间的栈，不能证明它就是持续热点。线程名、`RUNNABLE` 状态也不等于该线程一定在消耗 CPU。

### 3. 请求卡住时区分锁、连接池与网络等待

比较两到三份 `Thread.print -l`：长期 `BLOCKED` 的线程查看它等待的 monitor 以及持有锁的线程；大量线程停在 Hikari 获取连接的位置时，检查连接池 active/idle/pending、慢 SQL 和事务时间；停在 Socket 读取/连接调用时，再核对下游 DNS、连接超时、读超时和远端延迟。不要通过无条件扩大线程池掩盖连接池耗尽或慢下游。

线程转储可能同时包含 SQL、URL、用户标识和业务参数，保存到受限目录，按组织的数据保留策略清理；不要把原始文件贴到公开工单。

### 4. 堆增长时先看回收后的基线

~~~bash
# 查看对象数量和大小的近似排序；大进程上运行可能产生明显开销。
jcmd <pid> GC.class_histogram

# 若确认需要保留证据，再将堆转储写到空间充足且访问受控的位置。
# 堆转储可能触发明显停顿，并包含用户数据、令牌或业务对象。
jcmd <pid> GC.heap_dump /safe/restricted/path/heap.hprof
~~~

GC 日志中关注暂停原因和时长、回收前后堆占用以及老年代回收后基线是否持续升高。回收后占用缓慢上升提示有对象被长期引用，但还要区分缓存增长、负载爬升和泄漏；一次 Full GC 或某个高水位不能单独证明内存泄漏。

JDK 11 可在受控重启时启用滚动 GC 日志，例如：

~~~text
-Xlog:gc*,safepoint:file=/var/log/app/gc.log:time,uptime,level,tags:filecount=5,filesize=20M
~~~

启动参数变更需走部署变更并预留磁盘空间。若生产没有记录 GC 日志，不能在故障发生后补出历史数据；要先在测试环境验证日志格式、轮转和采集。

### 5. RSS 上升时检查堆外内存和线程预算

若 JDK 启动时已启用 Native Memory Tracking，可查询 JVM 管理的本地内存分类：

~~~bash
# NMT 需要在 JVM 启动参数中开启；未开启时该命令不会提供完整分类。
jcmd <pid> VM.native_memory summary

# 对照线程数量、容器限额、直接内存上限和 OS 指标，不能只盯 Xmx。
ps -o pid,nlwp,rss,vsz,cmd -p <pid>
~~~

NMT 不能覆盖所有第三方 Native 分配，也有采集成本；没有 NMT 数据时结合线程数、`-XX:MaxDirectMemorySize`、容器内存和进程 RSS 分析。不要把“堆没满”直接等同于“进程还有可用内存”。

## 常见误区

- Java 有 GC 不代表没有内存泄漏；只要对象仍可达，它就不会被回收。
- 增大 -Xmx 只能改变堆上限，不能修复无界缓存、线程泄漏或直接内存问题。
- -Xms 是初始/最小堆设置，-Xmx 是最大堆设置；具体行为还受 JVM 和容器配置影响。
- System.gc() 不是立即释放内存的命令，生产逻辑不能依赖它。
- 堆内存占用不等于整个 Java 进程占用；线程栈和直接内存也需要预算。
- 单看 GC 次数不够；要看暂停时间、回收前后占用、请求延迟和吞吐。
- Heap dump 和线程 dump 可能包含敏感数据，分享之前要审批存储位置并脱敏。
