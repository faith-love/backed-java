# MySQL 与 Redis：表结构、查询、缓存和一致性

MySQL 和 Redis 都能保存数据，但解决的问题与访问模型不同。理解差异有助于排查“为什么数据库有记录，页面却显示旧数据”或“查询突然变慢”。

关系型、缓存型、时序型、文档型与搜索/分析存储的选型总览见[数据库类型全景](./database-types.md)；本页集中讲 MySQL 与 Redis 的表设计、缓存一致性和使用边界。

MySQL 通常是结构化业务数据的权威来源；Redis 通常用于缓存、短期状态、计数和协调。它们之间的关键问题不是“谁更快”，而是**哪一份数据是事实、丢失后能否恢复、并发更新如何判定成功**。

## 关系型数据库解决什么问题

MySQL 把数据组织为表、行和列，适合结构明确、有关联、需要约束或事务的数据。唯一约束避免重复，事务组合多条写操作，SQL 查询负责筛选和聚合。

用户、角色、仪表盘页面元数据和订单等需要长期保存并维护关系的数据，通常保存在关系型数据库。

~~~sql
-- 按状态过滤用户，并用主键排序保证分页顺序稳定。
SELECT id, user_name, status
FROM sys_user
WHERE status = 1
ORDER BY id
LIMIT 20 OFFSET 0;
~~~

**解决的问题：** 持久、结构化且可约束的数据管理，并提供事务和灵活查询。

**取舍：** 关系查询能力强，但要考虑索引、锁、事务和容量。索引能提高特定查询速度，也增加写入成本、磁盘占用和维护开销。

## 表结构、约束与索引

### 主键与唯一约束

主键给每一行提供稳定身份；唯一约束阻止关键字段重复。它们解决“数据如何唯一定位”和“如何由数据库最后把关”。

唯一性必须由数据库约束兜底，因为并发请求可能同时通过应用层“先查再插”的检查。

### 索引

索引通过额外的数据结构加快特定条件下的查找，解决大表上扫描全部行的成本问题。MySQL InnoDB 的普通索引通常基于 B+Tree；它需要额外磁盘空间，并让 INSERT/UPDATE/DELETE 同时维护索引。

#### 复合索引与最左前缀

假设列表常按“租户、状态、创建时间、ID”筛选和排序，可以考虑索引：

```sql
-- 先等值条件，再范围/排序字段；最终顺序要用实际查询和 EXPLAIN 验证。
CREATE INDEX idx_order_tenant_status_created_id
    ON orders (tenant_id, status, created_at, id);
```

复合索引的字段顺序会影响可用前缀：`(tenant_id, status, created_at)` 通常能支持从 `tenant_id` 开始的条件，但不一定能有效支持只按 `status` 的查询。范围条件、排序方向、字段选择性和 MySQL 版本也会影响优化器决策，不能只背一个“固定口诀”。

#### 覆盖索引与不可搜索表达式

覆盖索引包含查询所需的过滤、排序和返回字段，数据库可能只读取索引而不用回表；但把太多列塞进索引会增加写放大和存储。

下面这种写法可能让普通 `created_at` 索引难以直接使用：

```sql
-- 对索引列套函数，可能让条件无法使用普通范围查找。
WHERE DATE(created_at) = '2026-11-17'

-- 改为半开区间，通常更利于使用时间索引，也避免一天最后一刻精度问题。
WHERE created_at >= '2026-11-17 00:00:00'
  AND created_at <  '2026-11-18 00:00:00'
```

同样要避免隐式类型转换、前置通配符 `%keyword` 和对索引列进行计算后比较。搜索需求若必须包含任意位置文本，评估全文索引或搜索服务，而不是误以为普通 B+Tree 一定能加速。

#### 用 `EXPLAIN` 验证，而不是猜索引

```sql
-- 用与生产相同的代表性参数检查执行计划；MySQL 8.0.18+ 可使用 EXPLAIN ANALYZE 实际执行。
EXPLAIN
SELECT id, status, created_at
FROM orders
WHERE tenant_id = 1001
  AND status = 'PAID'
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

重点观察访问类型、候选 key、预估扫描行数、过滤比例、排序是否额外使用 filesort、是否需要回表。执行计划只是对当前统计信息和参数的估算；线上验证还需要慢查询日志、真实耗时、返回行数和数据库负载。

### 字段类型、NULL 与约束

数据库结构是后端契约的一部分，常见设计决策会直接影响前端展示和校验：

| 字段 | 建议考虑 | 可能影响 |
|---|---|---|
| 主键/外键 | 身份稳定性、关联约束、分布式 ID | 前端 ID 精度、删除顺序、引用完整性 |
| 金额 | `DECIMAL(p,s)` 与明确币种 | 小数精度、格式化和汇总准确性 |
| 时间 | UTC/时区策略、精度、范围查询 | 日期筛选边界和跨区展示 |
| 状态 | 有限枚举值和默认状态 | 下拉选项、兼容旧客户端 |
| 可空字段 | NULL 是否有独立业务含义 | 未填写、未知、不适用不能混为一谈 |
| 字符串 | 长度、字符集、大小写比较规则 | 校验长度、唯一性与搜索结果 |
| JSON | 是否真的需要半结构化字段 | 索引、验证、版本迁移和字段兼容 |

`NOT NULL`、`UNIQUE`、`CHECK`、外键等约束在数据库提交处兜底，特别是在并发下避免应用层“先查不存在、再插入”发生竞态。约束错误需要在服务边界转换为稳定的业务冲突响应，不能直接把数据库错误文本返回浏览器。

### 规范化与反范式

- 规范化减少重复存储，降低更新不一致。例如客户名称只在客户表维护，订单保存 customer_id。
- 反范式可能减少读取 JOIN 或聚合成本，例如订单保存下单时的商品名称和单价快照。
- 快照字段要说明是历史事实还是实时引用。订单行价格通常应保留购买时价格；用户头像 URL 通常不应复制成订单快照。
- 冗余数据要定义更新策略、来源字段和修复任务，避免数据修复时不知道哪一列是权威值。

不要只因为 Entity 有关联就把所有关系映射成自动级联保存；更新接口应明确哪些字段可由前端修改，哪些由数据库或服务端计算。

### 事务与隔离

事务保证一组写操作整体提交或回滚。隔离级别控制并发事务之间能看到的数据，隔离越强通常限制越多；默认行为取决于数据库版本和配置。

出现重复扣减、读到旧值或锁等待时，检查事务边界、并发访问顺序、隔离级别和索引。

#### 并发事务会出现什么现象

| 现象 | 含义 | 例子 |
|---|---|---|
| 脏读 | 读到另一个尚未提交、之后可能回滚的数据 | 查询到一笔最终失败的支付状态 |
| 不可重复读 | 同一事务两次读同一行，另一个事务已提交修改 | 页面计算总额前后读到不同余额 |
| 幻读 | 同一条件再次查询，出现另一事务新插入/删除的匹配行 | 两次查“待审批记录”数量不同 |
| 丢失更新 | 后写覆盖先写，导致一个修改消失 | 两个编辑页面都从版本 3 保存，后者覆盖前者 |
| 死锁 | 两个事务互相等待对方持有的锁 | 两个流程以相反顺序更新 account A/B |

InnoDB 在常见默认配置下使用 Repeatable Read，但最终行为还受数据库版本、索引、读写语句和锁定读方式影响。遇到并发问题应复现具体 SQL 顺序并看锁信息，不能只凭异常名称猜隔离级别。

#### 锁等待与死锁的处理

1. 缩短事务，不要在持有数据库锁时等待用户输入或慢远程请求。
2. 多行更新按固定顺序访问，例如总是按主键升序锁行。
3. 给 `UPDATE/DELETE` 条件和外键字段建立合理索引，减少锁扫描范围。
4. 死锁是数据库为保护系统选择回滚一个事务；应用应识别后有限重试整个幂等事务。
5. 查看数据库死锁日志、当前锁等待、事务持续时间和执行 SQL，不要只把事务超时调大。

## 分页与排序

LIMIT/OFFSET 是常用分页方式。没有 ORDER BY 时，数据库不保证行顺序；排序字段不唯一时，翻页边界可能不稳定。大偏移量分页还可能扫描并丢弃大量行。

~~~sql
-- 使用唯一递增 ID 作为游标，从上次看到的记录之后继续读取。
SELECT id, user_name
FROM sys_user
WHERE id > 1000
ORDER BY id
LIMIT 20;
~~~

### 列表筛选如何影响 SQL 与索引

假设前端发送：

```text
GET /api/orders?status=PAID&createdFrom=2026-11-01&pageNum=1&pageSize=20
```

服务端应把筛选字段绑定为值参数，并确保数据范围条件来自认证上下文：

```sql
-- 查询 DTO 提供状态和时间范围；tenant_id 必须由服务端身份上下文确定。
SELECT id, status, created_at, amount
FROM orders
WHERE tenant_id = ?
  AND status = ?
  AND created_at >= ?
ORDER BY created_at DESC, id DESC
LIMIT ?;
```

然后用执行计划验证索引是否匹配。前端把 `status` 加到 Query 上，只能证明浏览器发了参数；不能证明 Controller 绑定正确、Service 没有覆盖条件、Mapper 已把它加入 SQL，或数据库使用了预期索引。

### Offset 与游标分页

Offset 分页便于跳页并返回 total，但深页可能扫描并丢弃大量数据；数据不断插入时，用户翻页可能看到重复或漏行。游标/Keyset 分页使用上页最后一条记录作为边界，适合时间线、审计日志和无限滚动，但不擅长任意跳到第 N 页。

若排序字段可能重复，要用唯一键构成稳定游标：

```sql
-- 游标保存上页最后一条记录的 (created_at, id)。
SELECT id, created_at, status
FROM orders
WHERE tenant_id = ?
  AND (created_at, id) < (?, ?)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

`COUNT(*)` 可能比取当前页更贵。若数据量极大，可以定义估算 total、延迟 total 或“是否还有下一页”的 API 契约；前端分页组件需要知道 total 是否精确，不能悄悄改变响应语义。

## Redis 解决什么问题

Redis 是内存型键值数据存储，适合低延迟读取、短期状态、计数和分布式数据结构。它也支持持久化，但不能因“读取快”就把它当成关系数据库的替代品。

- 缓存减少重复访问数据库或远程 API。
- 计数和限流记录原子计数或时间窗。
- 短期状态保存验证码、临时会话或任务状态。
- Set、Sorted Set、Hash 等结构支持集合、排序和映射类操作。

每种用途都要定义过期、数据丢失和恢复语义。缓存丢失通常应允许从权威数据源重建；需要永久保存的数据不能只依赖未备份的缓存。

### 常见数据结构与使用场景

| Redis 结构 | 适合的数据形状 | 常见用途 | 使用边界 |
|---|---|---|---|
| String | 单个值/序列化对象/计数 | token、短期详情缓存、原子计数 | 对象缓存要控制序列化版本和大小 |
| Hash | 一个对象的多个字段 | 配置、会话字段、轻量对象缓存 | 多字段更新要考虑一致性和过期策略 |
| List | 按顺序排列的元素 | 简单队列、最近记录 | 不等同于可靠消息队列，持久消费语义要另设 |
| Set | 唯一元素集合 | 标签集合、去重成员 | 大集合遍历可能产生阻塞，应使用 scan/分页方式 |
| Sorted Set | 成员 + score 排序 | 排行榜、延迟任务索引 | 高基数/高频更新要评估内存和 score 精度 |
| Stream | 可确认的消息流 | 轻量事件流和消费组 | 需要管理积压、确认、重试和裁剪 |
| Bitmap/HyperLogLog | 位集合/基数估算 | 签到、近似 UV | 近似结构不适合要求精确结算的数据 |

选择结构前先写出访问模式：按什么 key 读取、是否要排序、需要原子操作还是事务、是否要求可靠消费、key 多久过期。不能只因 Redis API 有一个数据结构，就把它当作任意数据库模型。

### 原子命令、Lua 与原子性边界

单条 Redis 命令通常是原子执行的，例如 `INCR` 可以安全地并发递增。但“先读、判断、再写”由多个命令组成时，其他客户端可能插入执行；此时需要 Lua 脚本、事务/Watch，或把业务重新设计成一条原子命令。

```text
错误的限额检查：GET count -> if count < limit -> INCR count
两个请求可能同时读到 limit-1，然后都通过。

更安全：Lua 中检查并递增，在一个脚本执行期间保持原子。
```

Redis 原子性只保护 Redis 中的操作，不会让 Redis 与 MySQL 一起提交。支付余额、库存权威值等重要状态应该由数据库约束/事务或专门的账本模型保护，Redis 可作为加速层或协调手段。

## 缓存旁路模式

Cache Aside 让应用控制缓存和数据库的读写顺序。读取先查缓存，未命中再读数据库并写缓存；更新通常先写数据库，再删除缓存。

~~~java
// 按用户 ID 构造缓存键，并使用业务前缀避免与其他对象冲突。
String key = "user:" + userId;

// 先从缓存取值；项目通常会用统一 Cache 封装处理序列化。
UserView cached = cache.get(key, UserView.class);
if (cached != null) {
    // 命中时直接返回，减少数据库读取。
    return cached;
}

// 缓存未命中时读取权威数据源。
UserView result = userRepository.findViewById(userId);
if (result != null) {
    // 设置有限 TTL，避免旧值永久存在。
    cache.set(key, result, Duration.ofMinutes(10));
}
// 返回查到的结果；不存在时由接口约定处理空值。
return result;
~~~

**解决的问题：** 热点数据反复读取时，减少数据库压力和接口延迟。

**取舍：** 缓存引入过期、并发更新和短暂不一致。更新数据库与删除缓存之间仍可能出现竞态，业务需要定义可接受的一致性窗口。

### 缓存 key 必须包含影响结果的维度

一个缓存 key 不能只看对象 ID。以下维度只要影响响应，就必须体现在 key 或访问授权之后：

- 租户/组织/数据范围。
- 用户身份或角色权限。
- 语言、时区、币种和展示版本。
- 查询筛选、排序、分页游标。
- DTO/缓存 schema 版本。

例如 `order:detail:{id}` 可能把不同租户的可见字段混在一起；至少需要 `tenant:{tenantId}:order:{id}`，并且命中缓存后仍要验证资源权限。缓存 key 不是权限证明。

### 更新缓存的顺序与竞态

常见 Cache Aside 写流程是：**先提交数据库，再删除缓存**。先删缓存再写数据库可能让另一个请求在中间读到旧 DB 值并把旧值重新写回缓存。

但先更新 DB 再删缓存仍可能有竞态：删除失败、并发旧读回填、进程提交后崩溃等。可按一致性要求选择：

1. 允许短暂旧值：DB 提交后删除缓存，设置合理 TTL，并监控删除失败。
2. 需要可靠失效：在同一 DB 事务写 Outbox 事件，提交后消费者重试删除缓存。
3. 需要版本隔离：使用数据版本号/缓存版本 key，避免旧请求回填覆盖新版本。
4. 多副本本地缓存：使用变更广播、短 TTL 或不在本地缓存高一致性数据。

延迟双删是一种在特定并发模式下减少旧值窗口的补偿方法，不是原子一致性证明；延迟时间、重试和进程崩溃都需要单独设计。

## 缓存常见故障

- 穿透：不断请求不存在的数据。可用参数校验、短期空值缓存或布隆过滤器。
- 击穿：热点键过期后，大量请求同时回源。可用请求合并、互斥重建或逻辑过期。
- 雪崩：大量键同时过期或 Redis 故障。可错开 TTL，并设计回源限流和降级。
- 不一致：数据库更新后旧缓存仍存在。明确写入顺序、失效策略和修复方式。
- Key 冲突：多个业务误用同名键。采用业务前缀、环境隔离和清晰编码规则。

不要把用户输入拼成 Redis 命令文本；通过客户端 API 传入键和值，并设置 TTL、容量和访问权限。

### TTL、内存淘汰和持久化

- **TTL**：明确每类键的有效期并增加随机抖动，避免大量 key 同时过期。没有 TTL 的缓存可能永久占用内存。
- **淘汰策略**：Redis 达到 `maxmemory` 后按配置策略删除键；如果缓存与任务状态混用，淘汰可能破坏业务状态。
- **RDB**：周期性快照，恢复快但可能丢失最近一次快照后的数据。
- **AOF**：记录写命令，数据持久性通常更强，但文件与重写管理有成本。
- **复制/哨兵/集群**：提供复制、故障转移或分片能力；复制延迟、脑裂窗口和集群槽迁移仍会影响访问。

Redis 是否开启持久化、备份和高可用要看部署配置。对缓存而言重启后回源是可接受的前提；对验证码、任务状态或限流计数则要明确丢失会带来的体验/安全影响。

## Redis 实战：原子限流与锁的适用边界

### 固定窗口计数

```lua
-- KEYS[1] 是服务端构造的限流 key；ARGV[1] 为窗口秒数，ARGV[2] 为阈值。
local current = redis.call('INCR', KEYS[1])
if current == 1 then
  redis.call('EXPIRE', KEYS[1], ARGV[1])
end
if current > tonumber(ARGV[2]) then
  return 0
end
return 1
```

固定窗口允许边界突发：窗口最后一秒和下一窗口第一秒可能连续通过两倍阈值。若需要更平滑的限流，可以使用滑动窗口或令牌桶，并明确按用户、租户、IP、接口还是全局限流。不要让客户端随意构造 Redis key，也不要把敏感 Token 放进 key。

### 分布式锁的边界

简单分布式锁通常需要原子 `SET key value NX PX ttl`，释放时必须比较 value 与当前 owner 后再删除，防止锁超时后误删新持有者的锁。长任务还要续租/租约失效策略；如果持锁进程停顿超过 TTL，另一个进程可能开始操作，所以被保护资源还应使用数据库版本或 fencing token 防止旧持有者继续写入。

分布式锁适合降低重复工作或协调短任务，不应代替数据库唯一约束、乐观锁和业务幂等。锁服务分区、超时和应用停顿都会使“我以为自己持锁”的假设失效。

## Redis 故障与降级行为

对每种 Redis 使用点，写清楚 Redis 不可用时的选择：

| 用途 | 可以考虑的行为 | 不能默认采取的行为 |
|---|---|---|
| 可重建缓存 | 有界回源、短期降级、返回明确超时 | 所有请求同时击穿数据库 |
| 限流 | 保守拒绝、局部内存限流或明确降级 | Redis 失败就无限放行敏感接口 |
| 登录状态/验证码 | 明确认证失败并要求重试 | 无法校验就默认认证成功 |
| 异步任务状态 | 返回“状态暂不可用”或读持久存储 | 把任务误报为成功 |
| 分布式锁 | 失败时按关键程度拒绝或排队 | 锁获取失败仍执行关键写操作 |

降级分支应有指标和告警，并限制回源并发；否则 Redis 故障可能继续演变成数据库雪崩。

## 本项目中的数据源区分

数据中台至少需要区分应用配置数据与图表运行时业务数据：

1. 应用配置库保存页面、图表配置和权限关系。
2. 图表数据按图表的数据集配置，从外部数据源读取。

所以页面配置正常打开，图表仍可能因为外部数据源不可达而为空。排查时确认当前查询的是配置库还是图表数据源，并查看对应连接、权限和查询日志；连接细节以当前环境配置为准。

在当前 `datacenter-cloud` 中，可以结合 [项目地图](../project-map.md) 以及 `gykj-modules/gykj-cloud` 的数据源服务阅读动态数据源和外部 Schema。配置文件可能包含敏感连接信息，学习时只记录配置项名称和数据流向，不复制账号、密码或地址。

Redis 侧可从 `gykj-common/gykj-common-redis` 的配置和 `RedisService` 阅读 key/value 序列化、TTL 与数据结构操作。`@EnableCaching` 只说明 Spring Cache 基础设施可用，具体业务是否缓存仍要搜索 `@Cacheable` 或 `RedisService` 调用点。

本页负责 MySQL/Redis 的概念基础；更深入的 SQL 结构见 [SQL 查询与写入实战](./sql-practice.md)，InnoDB 锁/复制/备份见 [MySQL 生产机制与运维](./mysql-operations.md)，Redis 高可用、内存和 Stream 语义见 [Redis 运维与消息语义](./redis-operations.md)。

## 前端联调检查

- 刷新后仍显示旧值：分别查浏览器缓存、服务端 Redis 与数据库更新时间。
- 列表顺序不稳定：确认后端设置了稳定排序。
- 翻页重复或漏行：记录页码、排序字段与边界数据。
- 图表与管理列表内容不一致：确认两者是否使用相同数据源和筛选条件。
- Redis 故障：观察服务是否回源、是否限流，以及 UI 能否区分降级结果。
- 列表筛选无效：比较 URL Query、Controller DTO、Service 条件、最终 SQL 与 `EXPLAIN` 计划。
- 保存冲突：确认后端是否检查版本号/影响行数，前端是否能识别 409 并刷新数据。
- 多租户详情读取：检查 DB 查询条件和缓存 key 是否都包含可信租户范围。
- 金额/时间偏差：核对 DB 列类型、Java `BigDecimal`/时间类型、时区和 JSON 序列化格式。
