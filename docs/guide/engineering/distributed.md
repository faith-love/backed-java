# 微服务与消息系统

微服务把一个大型应用拆成多个可独立开发、部署和扩容的服务。拆分后，每个服务可以围绕清楚的业务职责变化；代价是一次业务操作可能跨越网络、进程和数据库边界。网络会超时，服务会重启，消息会重复投递，因此分布式系统需要显式处理发现、路由、超时、失败、数据一致性和追踪问题。

本页聚焦跨服务协作的通用机制和设计取舍。Nacos、Gateway、Sentinel、Seata 的具体配置、命令和排错步骤集中在[微服务工具专题](./microservice-tools.md)与[Nacos 专题](./nacos.md)，避免把某个工具的 YAML 示例误当成所有项目的通用配置。

## 什么时候需要微服务

**解决的问题：** 当一个应用的团队、业务模块、发布节奏或资源需求差异已经很大时，可以把相对独立的能力拆成服务，让它们分别发布和扩缩容。

**需要付出的代价：** 本地方法调用变成网络调用，原本单进程内的事务也不再覆盖所有服务。服务数量越多，部署、监控、权限、版本兼容和故障排查越复杂。若模块仍紧密共享同一数据表，拆开后往往只是增加网络跳转。

评估服务边界时可以问：它是否有清楚的业务职责？是否能独立部署？数据由谁负责写入？其他服务通过稳定接口访问，还是直接依赖它的数据库表？

### 服务边界与数据所有权

一个服务应负责自己领域数据的写入和约束。其他服务通过 API 或领域事件获得所需信息，不应直接修改它的数据库表；跨服务直连数据库会绕过权限、校验和业务状态机，使表结构变化同时破坏多个调用方。

同步查询适合调用方当前就需要结果的场景，但增加运行时依赖；异步事件适合通知“已经发生的事实”，可以解耦消费者，但调用方要接受延迟并查询最终处理状态。服务拆分前，先把模块间接口和数据责任分清；若多个模块必须共享同一张表和同一个事务，模块化单体可能更简单。

接口字段应采用向后兼容的演进方式：先新增可选字段，观察旧调用方退出，再删除旧字段。对关键消费者可加入接口契约测试，验证提供方的实际响应仍符合调用方依赖的字段、类型和错误语义。

## 服务发现：解决地址变化

容器或虚拟机重建后，实例 IP 和端口可能变化。把地址硬编码在调用方配置里会导致扩容、迁移和故障切换都要逐个改配置。注册中心提供服务名到健康实例的动态映射：服务启动时注册，健康检查持续更新状态，调用方或网关再从可用实例中选择目标。

服务发现主要解决“去哪里调用”，不代表“调用一定成功”。注册信息可能短暂过期，网络也可能在实例被标为健康后立即中断，所以仍需要连接超时、读取超时和失败处理。

~~~text
服务启动 -> 注册服务名和实例地址 -> 健康检查
调用方按服务名查询健康实例 -> 负载均衡选择一个实例 -> 发起请求
实例退出或不健康 -> 注册信息更新 -> 后续请求避开该实例
~~~

服务名相当于逻辑地址，注册中心记录实例的 IP、端口、元数据和健康状态。调用时常见两种路由方式：**客户端负载均衡**由调用方查询实例并自行选一个；**服务端/代理负载均衡**由网关或代理根据服务名选择实例。若客户端缓存了实例列表，注册变更到所有调用方刷新之间会有短暂传播延迟。

本地排错时分别核对应用是否成功注册、实例健康状态、调用方使用的命名空间/分组和网关路由目标。服务在 Nacos 页面显示在线不代表端口从调用方网络可达，也不代表应用业务依赖健康。

实例选择是负载均衡问题，常见策略包括：轮询适合实例能力接近且请求时长接近的场景；权重可逐步把流量切到新版本；最少连接数适合请求时长差异较大但需要维护活动连接数的客户端；按用户/订单 ID 哈希可让同一键较稳定地落到同一实例，但容易产生热点，也不应依赖它保存必须持久化的会话状态。健康检查只过滤已知不健康实例，不能消除检查间隔内的新故障。

本节只说明注册中心的通用职责，不重复某个客户端的配置项。Nacos 的命名空间、分组、健康检查、服务列表验证和配置发布步骤见 [Nacos 服务发现与配置中心](./nacos.md)。

## Gateway：统一外部入口

**解决的问题：** 前端不需要知道用户、报表和文件等每个后端服务的内部地址，也不必在各服务重复实现所有入口级处理。Gateway 根据路由规则把外部请求转发到目标服务，并可集中执行部分身份校验、限流、跨域处理、访问日志和路径改写。

浏览器到 Gateway 与 Gateway 到业务服务是两段独立的网络连接。浏览器看到的 URL 可能包含外部前缀，网关转发时又可能删掉或重写前缀，所以不能仅凭前端 URL 推断 Controller 的映射路径。

这里只讨论网关的职责和请求边界；Spring Cloud Gateway 的路由字段、路径改写和状态码排错见 [Gateway 工具专题](./microservice-tools.md#spring-cloud-gateway-从浏览器入口路由到服务)。

网关不是唯一的安全边界。内部服务若可以被其他网络直接访问，仍要按系统设计验证身份和权限；路径匹配错误则可能造成 404、转发到错误服务或绕过预期过滤。

### 一条 Gateway 路由要核对什么

请求进入网关后，常见步骤是匹配域名/路径/方法等 Predicate，执行过滤器，再通过逻辑服务名找到实例并转发；返回方向还可能处理 Header、响应码和日志。出现 404 时，按外部路径 → 路由 Predicate → 路径改写 → 下游 Controller 顺序比对；出现 502/503 时，再查服务实例、端口和连接；出现 504 时，核对每一跳的 timeout。

网关可负责入口认证、统一限流和跨域处理，但业务服务仍应验证操作权限和数据范围。只在网关校验身份而允许内部服务被绕过，可能形成越权入口。转发用户 Token 或用户上下文时，要核实 Header 是否会被覆盖、是否只传到可信内部服务，以及日志是否脱敏。

内部身份传递要使用受控的服务凭证或签名上下文，服务不能把任意客户端可写的 `X-User-Id`、`X-Tenant-Id` 当作可信身份。Gateway 认证通过也不意味着该用户有权操作每个下游资源；资源级授权仍应由负责该业务数据的服务执行。

## 远程调用：服务之间如何约定

Feign、HTTP Client 或 gRPC 把远程端点包装成调用接口，减少手工拼接 URL 和解析响应的样板。接口外观类似本地方法，但底层仍有网络延迟、序列化失败、连接耗尽、对端错误和超时等可能。

调用双方至少要约定：服务标识、路径和 HTTP 方法、请求字段、响应结构、错误语义、超时、认证方式以及兼容策略。发布新字段时，优先让新旧调用方短期内都能理解；删除或改变字段含义前要检查所有调用者。

~~~java
/**
 * 示例：声明远程服务的调用契约。
 * 方法调用会经过客户端代理并发起网络请求，不是普通的进程内调用。
 */
public interface UserProfileClient {

    /**
     * 按用户 ID 获取档案；远端不可用、超时或返回错误时调用方仍需处理失败。
     *
     * @param userId 用户标识
     * @return 远端服务返回的档案 DTO
     */
    UserProfileResponse getProfile(Long userId);
}
~~~

上例是表达契约的伪代码，真实项目通常通过 `@FeignClient`、请求映射注解和专用配置声明服务名、URL 与编码方式。读代码时从调用接口追到配置，再核对最终 URL 和失败处理逻辑。

### 同步调用还是异步事件

| 需要 | 同步 HTTP/RPC | 异步消息 |
|---|---|---|
| 当前请求立即依赖下游结果 | 适合，例如打开详情时查询用户权限 | 不适合让浏览器一直等待消费者处理 |
| 下游暂时不可用时仍接受请求 | 通常会失败或降级 | 可在持久化与确认配置满足时先接收，再异步处理 |
| 返回结果需要立即展示 | 可直接返回结果或明确错误 | 通常返回受理状态和业务 ID，前端再查询状态 |
| 调用关系 | 运行时耦合，双方都需在线 | 通过事件契约解耦，但引入延迟、重复和重放问题 |

异步接口可以返回 HTTP `202 Accepted` 和任务/业务 ID；这只表示请求已被接受处理，不表示最终业务成功。前端需要轮询、订阅事件或刷新状态，并让失败状态和超时状态可区分。

## 超时、重试与熔断：限制故障扩散

### 超时

**解决的问题：** 没有超时时，请求线程可能一直占用连接和工作线程等待一个已失联的下游。连接超时限制“建立连接要等多久”，读取超时限制“等待响应数据要多久”；连接池还有获取连接的等待时间。它们是不同阶段，不能只配置一个笼统的超时。

超时值要结合调用链和业务时限设置。若上游 2 秒就超时，下游却允许等 10 秒，上游已经失败时下游仍可能继续消耗资源。前端、网关、应用和远程客户端的等待上限应有清楚的预算关系。

常见超时可以分为连接池获取、TCP 建连、TLS 握手、响应读取和整次调用 deadline。配置 `read timeout` 不一定能限制连接池等待；客户端超时后也不一定能取消服务端已经开始的 SQL 或写入。写请求超时意味着“结果未知”，调用方应查询幂等键或业务状态，不应直接断定服务端没做事。

示例预算（仅说明上限关系，真实数值需按 SLO 和实测设定）：浏览器最多等 8 秒；Gateway 在约 7 秒内返回；业务服务在约 6 秒内完成；每个下游调用使用更小的剩余 deadline，且预留序列化、网络返回和错误映射时间。若多个下游串行调用，需把它们的最坏等待合计纳入上游预算；并行调用则要考虑最慢分支及取消行为。

### 重试

**解决的问题：** 短暂网络抖动或瞬时过载时，有限重试可能让一次可恢复失败成功。

**风险：** 重试会增加流量和延迟。创建订单、扣款等非幂等写操作若超时后重试，可能重复执行。多层都重试会放大请求数量；没有退避和次数上限也可能形成重试风暴。

重试前先确认操作是否幂等、失败发生在哪个阶段，并设置有限次数、退避策略和总耗时上限。已知参数错误或权限错误通常不应重试。

判断能否重试时先识别错误类别：参数校验、未授权、业务冲突等确定性错误通常不重试；连接中断、部分 502/503 和明确可恢复的限流可能适合有限重试；`429` 应遵守服务返回的 `Retry-After`（若有）。HTTP 方法名本身不能保证实现没有副作用；一次超时的 POST 可能已经创建成功，所以要先查询结果或带服务端幂等键再重试。

### 熔断与降级

**解决的问题：** 下游持续失败时，熔断器暂时阻止继续发送请求，避免等待和失败不断消耗上游资源；降级则为非核心能力提供受控的替代结果，例如返回可解释的“暂不可用”或不含个性化信息的静态数据。

熔断不是修复故障，也不是把所有异常伪装成成功。要明确统计哪些失败、开放多久、怎样半开探测、回退响应的业务含义，以及监控如何区分真实数据和降级数据。

典型熔断器有三个状态：**Closed** 正常放行并统计失败；达到阈值后进入 **Open**，短时间快速拒绝；等待窗口后到 **Half-Open**，只放少量探测请求，成功再关闭，失败则重新打开。阈值要结合窗口请求量，否则低流量服务的单次异常可能造成误熔断。连接超时、业务 4xx 和限流响应是否计入失败，需要按客户端框架和业务定义核实。

### Deadline、退避与故障隔离

单跳超时限制当前调用最多等待多久；deadline 是整条业务链路允许消耗的总时间。下游调用应传递剩余预算，而不是每经过一层就重新开始一段完整超时，否则一条链可能比浏览器的总等待上限长很多。

```text
# 重试只针对可恢复的瞬时错误，并设置尝试次数、总 deadline 和最大退避。
delay = min(maxDelay, baseDelay * 2^attempt) + random(0, jitter)

# 每次重试前检查总 deadline；预算耗尽就返回可区分的失败。
if now + delay >= deadline:
    stopRetrying()
```

指数退避减少连续冲击；随机抖动避免大量客户端在同一时刻一起重试。重试通常只适用于明确的瞬时错误，并且要求读取操作可安全重复或写操作有服务端幂等键。不要在浏览器、网关、Feign 和 SDK 多层同时配置多次重试；应设定单一重试责任层和全链路重试预算。

| 机制 | 解决的问题 | 设计重点 |
|---|---|---|
| Bulkhead（舱壁隔离） | 一个慢依赖占满所有线程或连接 | 按依赖隔离线程池、连接池或并发许可，限制队列长度 |
| Rate limit（限流） | 瞬时请求超过服务处理能力 | 明确按用户、租户或接口限额；拒绝时返回可识别状态和重试提示 |
| Load shedding（过载保护） | 过载请求继续排队导致延迟雪崩 | 优先拒绝低优先级请求，限制排队而不是无限占内存 |
| Backpressure（背压） | 生产速度长期高于消费速度 | 限制并发/缓冲、减慢上游或把任务持久化到有界队列 |

这些机制不能互相替代。增加队列长度会延迟失败但不会提升处理能力；无界线程池或无界内存队列可能把下游变慢转化为服务进程 OOM。

## 消息队列：把生产与处理解耦

**解决的问题：** 若一个请求需要通知多个下游或执行耗时任务，同步逐个调用会让用户等待，并让任一下游故障阻塞整条链路。消息队列允许生产者提交事件后尽早返回，由消费者异步处理，也能暂存短时间的流量峰值。

基本链路是：生产者发布消息到主题或队列，代理保存并按投递规则分发，消费者处理后确认。队列只能在配置和运行条件满足时提供相应持久化与投递保证；它不会自动保证业务操作只执行一次，也不会自动确保多个数据库和服务一起提交。

~~~text
业务服务 -> 发布 OrderCreated 事件 -> 消息代理持久化
                                      -> 通知服务消费并发送通知
                                      -> 统计服务消费并更新指标
~~~

关键设计点：

- **消息体：** 使用稳定、可版本化的事件字段，携带业务 ID 和事件 ID，避免把不必要的敏感信息复制进消息。
- **确认与重试：** 消费者完成业务处理后确认；失败时根据策略重试，持续失败要进入死信或人工排查流程。
- **幂等消费：** 同一事件可能重复到达，消费者应能识别已处理事件，或让重复执行不会改变最终结果。
- **顺序：** 只在业务确实要求时设计分区键或顺序处理；并行消费可能改变不同消息的完成顺序。
- **可观测性：** 日志和指标记录消息 ID、业务 ID、消费次数和最终状态，便于追踪从发布到处理的完整路径。

### 投递语义：生产确认和消费 ACK 是两件事

| 语义 | 典型做法 | 失败窗口 |
|---|---|---|
| 至多一次（at-most-once） | 先确认/提交消费位置，再处理消息 | 处理前进程崩溃可能丢消息，但通常不重复 |
| 至少一次（at-least-once） | 处理成功后再 ACK/提交消费位置 | 业务提交后 ACK 前进程崩溃，消息可能再次投递 |
| 业务上的有效一次 | 至少一次投递，加唯一事件 ID、幂等写入或本地事务 | 只在设计覆盖的业务状态和存储边界内成立，不代表跨任意数据库/服务全局恰好执行一次 |

**生产者确认**表示消息代理已按其配置接受消息，确认范围取决于持久化、复制和刷盘策略；它不代表消费者已收到或业务已经完成。**消费者 ACK/offset commit**表示消费者告诉代理某条消息或某个位置处理到哪一步；它不自动和业务数据库事务原子提交。

常见的至少一次消费顺序是：读取消息 → 在本地数据库事务内校验幂等键并更新业务 → 提交数据库 → ACK/提交 offset。若数据库提交后、ACK 前进程崩溃，代理会再次投递，所以幂等记录要与业务变更处于同一事务边界。

不同代理的消费确认模型有差别：RabbitMQ 通常逐条 ACK/NACK；Redis Streams 用 `XACK` 把消息从消费组的 pending 集合确认掉；Kafka 按分区提交“下一条要消费的 offset”，不是对每条消息做同样的 ACK。Kafka 并行处理时不能提交越过尚未完成记录的 offset，否则进程重启后可能跳过工作。

消费者幂等通常把“处理记录”和业务更新放在一个本地事务中：

```sql
-- 开始消费者所在服务的本地事务。
START TRANSACTION;

-- event_id 建唯一约束；重复时识别为已处理，不再重复改变业务状态。
INSERT INTO processed_event (event_id, processed_at)
VALUES (?, CURRENT_TIMESTAMP);

-- 根据事件更新本服务拥有的数据；应再次校验当前业务状态和租户范围。
UPDATE order_projection
SET status = ?
WHERE order_id = ?;

-- 处理记录和业务更新一起提交，再由消费者客户端向代理 ACK/提交 offset。
COMMIT;
```

若 `event_id` 唯一冲突，按“已处理”规则返回并 ACK；若事务失败则回滚并按退避策略重试。真实实现需区分唯一冲突与其他数据库异常，不能吞掉所有异常后确认消息。

### 常见消息系统的使用侧重点

| 系统 | 常见模型 | 常见场景 | 需要核实的边界 |
|---|---|---|---|
| RabbitMQ | Exchange 路由到 Queue，消费者 ACK | 任务分发、灵活路由、工作队列 | Publisher confirm、持久队列/消息、重投递和死信配置需分别确认 |
| Kafka | 持久化分区日志、Consumer Group 与 offset | 高吞吐事件流、日志、可回放数据管道 | 顺序通常只保证在分区内；offset 提交和外部数据库提交不天然原子 |
| RocketMQ | Topic、队列、消费组以及事务/延迟等能力 | 业务消息、顺序/延迟消息等场景 | 具体能力和事务消息语义依版本及配置；仍需处理业务幂等 |
| Redis Streams | Stream、Consumer Group、pending entry 和 ACK | 已有 Redis 环境中的轻量内部队列 | 数据耐久性受 AOF/RDB、复制和故障转移影响；不应默认等同于专用消息系统 |

选型要按消息量、保留和回放需求、顺序范围、运维能力、事务/确认语义及容灾目标比较，不能只比较产品名称或吞吐宣传值。

Kafka 的一个分区在同一 Consumer Group 内通常只分配给一个消费者处理；不同 group 可各自完整读取同一事件流。RabbitMQ 的工作队列一般由其中一个消费者处理一条消息；需要广播给多个独立消费者时，要使用 Exchange 将事件路由到各自队列。Redis Streams 的 Consumer Group 把消息分配给组内消费者，并用 pending 列表记录未确认消息。配置消费者组前，要先画出“一条消息需要被哪些独立业务各处理一次”。

### 顺序、重试、死信和积压

- 只有同一业务实体的事件需要顺序时，才用订单 ID 等字段作为分区/路由键；这样该实体落到同一队列或分区，但可能形成热点。
- 重试要有限次数和退避。反复失败的消息应隔离到死信队列（DLQ）或错误记录，保留失败原因和原始事件 ID，不能无限快速重投。
- 队列积压代表生产速率超过消费能力或消费者异常；观察队列深度、最老消息年龄、生产/消费速率、重试数和 DLQ 数量。
- 扩大消费者并发前先确认分区数、数据库连接池和下游容量，避免把消息积压转化为数据库过载。
- 消息 schema 要允许新旧消费者短暂共存；添加可选字段通常比改字段含义或直接删字段安全。
- 消息只携带完成处理所需的 ID 和字段；文件、图片或超大报表应放到对象存储，事件里传引用和校验摘要，避免大消息拖慢复制、重试和死信排查。
- 重放 DLQ 前要确认消费者版本、业务状态、下游容量和幂等记录；无条件批量重放可能再次触发付款、短信或外部 API 副作用。

## 幂等：让重复请求安全

**解决的问题：** 网络超时只能说明调用方没有在期限内收到结果，不能证明服务端没有完成写入。用户重试、网关重发或队列重复投递都可能让同一业务意图到达多次。

幂等意味着相同业务请求重复执行后，业务结果与执行一次相同。常见做法是使用由客户端或上游生成的幂等键，在数据库中以唯一约束防止重复创建；也可以记录事件 ID 和处理状态。幂等记录的作用范围、过期时间和并发冲突行为必须与业务一起定义。

~~~text
收到请求 -> 以幂等键尝试创建处理记录
          -> 已存在且已完成：返回之前的结果
          -> 首次创建成功：执行业务并保存结果
          -> 执行失败：按明确状态恢复或允许安全重试
~~~

仅在内存 Set 中记住处理过的 ID 不适用于多实例服务和进程重启；只生成 UUID 也无效，除非服务端持久化并检查该键。

### HTTP 写请求的幂等键设计

前端在用户发起一次“创建订单/支付”意图时生成 `Idempotency-Key`，网络重试时复用同一个键；用户主动再次创建新订单时要使用新键。服务端将键限定在租户/用户和操作范围内，并保存请求摘要：

```http
# 每次新的用户意图生成新键；同一意图的网络重试保持该键不变。
POST /api/orders
Idempotency-Key: 8a725f54-7c2f-4f2a-8f52-bd27f57a8603
Content-Type: application/json

{"productId": "P-100", "quantity": 2}
```

服务端收到同键请求时要区分：已完成且请求摘要相同则返回之前的业务结果；仍在处理中则返回明确的处理中响应；同键但请求内容不同则拒绝（常见为 `409 Conflict`）。唯一约束负责处理两个相同键并发到达的竞态；只在缓存里 `GET` 再 `SET` 仍可能被并发请求穿透。

```sql
-- 每个租户、操作和幂等键的组合只能有一条记录，数据库唯一键处理并发竞争。
CREATE TABLE api_idempotency (
    tenant_id BIGINT NOT NULL COMMENT '租户范围，避免不同租户互相冲突',
    operation VARCHAR(80) NOT NULL COMMENT '操作名称，例如 create-order',
    idempotency_key VARCHAR(128) NOT NULL COMMENT '客户端为一次业务意图生成的键',
    request_hash CHAR(64) NOT NULL COMMENT '规范化请求体的摘要，用于检测同键异参',
    status VARCHAR(20) NOT NULL COMMENT 'PROCESSING、SUCCEEDED 或允许重试的 FAILED',
    response_body JSON NULL COMMENT '成功后保存可安全重放的响应结果',
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '用于审计和保留期清理',
    PRIMARY KEY (tenant_id, operation, idempotency_key)
);
```

幂等记录应与关键业务写入在同一本地事务里，或由有恢复能力的状态机管理。设置记录保留期时，要覆盖客户端、网关和支付渠道可能的重试窗口；清理过早会让旧请求再次产生副作用。支付场景可参考[线上支付示例](../../examples/online-payment)，把渠道交易号、商户订单号和通知去重键分开理解。

## 分布式事务与最终一致性

**解决的问题：** 多个服务各自拥有数据库时，单个数据库事务无法原子地覆盖所有服务。常见业务通过本地事务、事件通知、重试、幂等和补偿动作逐步达到最终一致，而不是假定一次远程调用能共同提交。

例如订单创建与库存占用可以按业务状态机处理：订单先进入待确认状态，库存成功后确认，库存失败则取消订单。补偿动作也可能失败，需要保存操作进度、提供重试和人工处理入口。数据库 outbox 等模式用于缓解“本地数据已提交，但事件未成功发布”的双写问题；是否采用应看项目的消息和事务基础设施。

| 方案 | 怎样做 | 适合场景 | 主要代价 |
|---|---|---|---|
| 单库本地事务 | 多个表在同一数据库事务中提交或回滚 | 服务边界尚在同一数据库，业务允许单库设计 | 服务会共享部署和数据库边界 |
| XA/2PC | 协调者先让参与者 Prepare，再统一 Commit/Rollback | 参与资源支持、需要强事务语义且可接受锁定/协调成本 | 协调器故障、长事务、资源锁和可用性复杂度；不能跨任意 HTTP 服务自动生效 |
| TCC | Try 预留资源、Confirm 确认、Cancel 释放 | 有清楚预留/确认/取消语义的资金或库存流程 | 每个参与方都要实现幂等和补偿分支，开发及运维复杂 |
| Saga | 一系列本地事务，失败后执行业务补偿 | 流程长、跨多服务，允许最终一致与处理中状态 | 补偿不是回滚，必须处理补偿失败、重试和人工介入 |
| Outbox | 业务数据与待发事件同库同事务，后台可靠发布 | 解决“本地提交但事件没发出”的双写问题 | 通常至少一次投递，需幂等消费及 Outbox 清理/监控 |

选型顺序通常是先判断能否用一个数据库事务；跨服务后再问业务能否接受处理中和最终一致。不要因为项目依赖里出现某个分布式事务框架，就推断每个写入路径都受它保护。

前端可能看到处理中、待确认或失败状态。API 需要明确返回状态语义，并提供查询最终状态的方法；不要把异步接收成功误解为整个业务已经完成。

### Outbox：让业务提交和事件记录共用一个本地事务

直接执行“更新数据库，然后发送消息”存在双写窗口：数据库成功而消息发送失败时，下游永远不知道业务变化；先发消息再提交数据库则可能让消费者看到后来回滚的事实。Outbox 将待发布事件与业务数据放入同一个数据库事务：

```text
本地数据库事务：
  1. 更新订单为 PENDING
  2. 插入 outbox_event(event_id, type, payload, status=PENDING)
  3. 一起提交

Relay：查询待发布事件 -> 发布到 Broker -> 标记已发布/记录位点
消费者：按 event_id 去重 -> 更新自己的本地数据 -> 成功后 ACK
```

订单行和 Outbox 行必须使用同一个本地事务管理器及数据库连接边界。下面的 SQL 用占位符表示由 Mapper/JDBC 绑定的值；真实应用由一个事务方法执行两条写入，不能把发送消息放进数据库事务后就假设两种资源自动原子提交。

```sql
-- 开始当前服务数据库的本地事务。
START TRANSACTION;

-- 保存业务状态；业务行和事件行要么一起提交，要么一起回滚。
INSERT INTO orders (id, status, created_at)
VALUES (?, 'PENDING', CURRENT_TIMESTAMP);

-- 保存待发布事件；event_id 是消费者去重和排错使用的稳定 ID。
INSERT INTO outbox_event (event_id, event_type, aggregate_id, payload, status)
VALUES (?, 'OrderCreated', ?, ?, 'PENDING');

-- 一起提交订单和待发事件；之后由 relay 独立发布消息。
COMMIT;
```

如果 Relay 已发布消息、但在标记已发布前崩溃，恢复后可能再次发布。因此 Outbox 消费端仍要幂等。事件表还需要状态、重试次数、最后错误、创建时间和保留/清理策略；高吞吐场景可评估 CDC 读取 Outbox，避免频繁轮询数据库。

### Saga：用状态和补偿组织跨服务流程

Saga 把跨服务业务拆成一系列本地事务，每一步成功后推进状态；后续步骤失败时，执行业务补偿动作恢复可接受的业务状态。补偿不是数据库回滚，可能失败，也可能需要重试或人工处理。

```text
创建订单(PENDING)
  -> 预占库存成功(INVENTORY_RESERVED)
  -> 扣款成功(PAYMENT_CAPTURED)
  -> 确认订单(CONFIRMED)

若扣款失败：释放库存 -> 订单标记 CANCELLED
若释放库存失败：记录补偿待处理状态，持续重试并告警，不丢掉流程进度
```

每一步要有幂等键、明确的状态迁移和超时恢复策略。向用户返回“受理中”时，提供查询订单最终状态的接口；业务界面要能区分处理中、成功、失败和需要人工介入。

这里的 Saga 是业务流程模式；若项目使用 Seata，需要再检查选择的是 AT/TCC/Saga/XA 哪种实现、数据源代理和补偿配置。工具模式的适用条件与项目检查路径见 [Seata 专题](./microservice-tools.md#seata-跨服务数据库事务协调)。

### 一致性、可用性与分布式锁的边界

CAP 讨论的是网络分区发生时，分布式系统如何在一致性与可用性之间取舍：一致性通常指读到最新已提交结果的强一致语义；可用性指非故障节点仍能对请求返回结果。它不是脱离故障条件后“从三项里任意选两项”的简单口诀。产品要按操作决定：余额扣减可能宁可暂时拒绝，也不能接受旧值；商品浏览可接受短暂旧数据。

最终一致系统要定义用户能感知的读语义，例如保存后短期读主、返回 `PENDING` 并轮询状态、或在列表中展示“同步中”。缓存、搜索索引和异步报表常有延迟；不能在 UI 把“暂时查不到”直接显示为“记录不存在”或“操作失败”。

分布式锁适合短时协调，例如避免多个调度实例同时启动同一批可重复任务。锁会遇到租约过期、网络分区和进程暂停：旧持有者可能在锁过期后继续写入。关键数据正确性应由数据库唯一约束、条件更新或版本号兜底；若依赖租约锁保护外部写入，还需使用递增 fencing token，让资源端拒绝旧持有者的迟到写入。

## 分布式可观测性：让一条请求跨越多跳仍可追踪

同步 HTTP 调用通常通过 `traceparent` 等追踪 Header 在服务间传递 Trace 上下文；入口可以生成 `traceId`，每个服务记录自己的 span 和错误。异步事件要在消息 Header/属性里显式带上 trace context、业务 ID 和 message ID，消费者从上下文继续或关联新的 trace；只靠线程本地变量无法跨进程或队列传播。

排错时至少关注：

- **调用侧：** 依赖调用量、延迟分位数、错误率、超时、重试次数、熔断状态和连接池等待。
- **消息侧：** 生产确认失败、消费速率、积压数量、最老消息年龄、重试和 DLQ 数量。
- **业务侧：** 处理中订单数、状态停留时间、幂等冲突、补偿失败和人工处理队列。
- **日志关联：** `traceId`、requestId、业务 ID、eventId 和消费次数；不要把 Token、口令或不必要的个人信息放进标签。

Trace 用来关联一次调用路径，不应把高基数字段（例如每个用户 ID）无节制地作为指标标签；指标与日志的采样和保留也要控制成本。

## 在当前项目中追踪

1. 从前端 API 确认请求的完整 URL、方法、请求头与响应，再确认 Gateway 对路径做了什么处理。
2. 查 Gateway 路由、服务名和注册中心配置，确认浏览器请求最终到哪个服务。
3. 从 Controller 追到 Feign Client 或消息生产者，记录请求/事件字段及调用时序。
4. 找远程调用的超时、重试、熔断和 fallback 配置；确认 fallback 是否把失败误报成空数据或成功。
5. 如果经过消息队列，再查生产确认、消费确认、重试、死信、幂等记录和业务最终状态。
6. 用 requestId、traceId、业务 ID 或 messageId 串起各服务日志；没有统一追踪时，先记录每一跳的时间和结果。

目录、服务名和运行环境会随分支变化。用实际配置和调用代码验证后，再把调用链画成笔记。

项目根 POM 管理多个服务模块，`docker/docker-compose.yml` 描述 Gateway、认证和业务模块容器，`docker/docker-compose-base.yml` 描述本地基础设施服务。仓库中存在 Seata 相关依赖管理只能说明代码库具备相关依赖线索，不代表每个 Profile、服务或线上环境都启用了分布式事务；要继续检查实际依赖、注解、配置和运行日志。

## 常见误区

- 服务发现只解决实例寻址，不替代健康处理、超时和失败恢复。
- Gateway 返回 200 不一定表示下游业务成功；还要看响应体和错误包装。
- Feign 接口看起来像本地方法，调用却可能因网络、远端错误或序列化而失败。
- 设置重试不能自动获得可靠性；非幂等写操作可能被重复执行。
- fallback 返回空列表会让“服务不可用”看起来像“确实没有数据”，需保留可区分的状态。
- 消息已发送不代表消费者已处理，消费者已收到也不代表业务已提交。
- “恰好一次”投递不能替代业务幂等；通常要把重复处理纳入设计。
- 拆分更多服务会增加网络和运维边界，微服务不是所有项目的默认最优结构。
