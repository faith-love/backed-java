# 计算机网络基础

网络知识帮助解释请求为何打不开、偶发超时、返回代理错误，或浏览器提示跨域。Network 面板展示 HTTP 视角；服务器与代理日志补充 DNS、TCP、TLS 和转发过程。

## 从 URL 到响应

以 https://api.example.test/dashboard/list 为例：

1. 浏览器解析协议、主机、端口、路径和查询参数。
2. DNS 将主机名解析到网络地址。
3. 对 HTTP/1.1 和 HTTP/2，客户端与服务器先建立 TCP 连接。
4. HTTPS 通常在 TCP 连接上进行 TLS 握手并验证证书。
5. HTTP 请求在连接中传输；代理或网关可能继续发起新的下游连接。
6. 应用返回 HTTP 状态和响应体，代理再转回浏览器。

HTTP/3 是重要例外：它运行在 QUIC 之上，QUIC 使用 UDP 并整合 TLS 1.3 握手，不经过 TCP 建连。实际使用哪种 HTTP 版本由浏览器、服务端和中间代理协商决定；Network 面板可查看协议列。

任一步失败都可能表现为“接口请求失败”，但处理位置不同。

浏览器 Network 的 Timing 面板可以把等待粗略拆开：Queueing/Stalled（排队或等待连接）、DNS Lookup、Initial connection、SSL、Request sent、Waiting/TTFB（等待首字节）、Content Download。缓存命中、连接复用或 Service Worker 可能跳过 DNS/建连阶段，因此某项耗时为 0 不表示系统没有该机制。若 TTFB 很长，可能是代理排队、应用计算、数据库或下游调用；仅凭 TTFB 不能断言是 SQL。

## DNS：从名字找到网络地址

DNS 解决人使用域名而不是记 IP 的问题。解析失败时，请求还没有连接到 HTTP 服务。

常见问题包括域名无法解析、不同网络解析到不同地址、缓存保留旧地址。检查系统解析结果、浏览器请求域名和代理日志；不要只改 hosts 来掩盖环境故障。

一次 DNS 查询可能经过浏览器缓存、操作系统缓存、企业 DNS 或递归解析器，再由权威 DNS 返回 A/AAAA 记录；CNAME 会继续指向另一个名字。结果受 TTL 缓存，发布新地址后各客户端不会保证同时更新。VPN、公司网络和本地开发代理可能使用不同解析器，所以“同一域名在另一台机器可用”不能证明当前网络解析正确。

```sh
# 查看当前解析器返回的地址；要分别检查 A/IPv4 与 AAAA/IPv6 记录时可使用 nslookup 或 dig 的记录查询选项。
nslookup api.example.test

# 查看目标主机的路由路径；中间设备可能屏蔽探测，因此失败不等于 HTTPS 一定不可达。
traceroute api.example.test
```

## TCP：可靠传输与连接生命周期

TCP 提供可靠、有序的字节流。连接建立、拥塞控制和重传都会引入延迟；连接池复用已有连接可以减少重复握手。

建立 TCP 连接时，客户端操作系统为连接分配临时源端口，目标由 IP 与端口共同定位；三次握手确认双方可以收发数据。端口监听、NAT、路由、防火墙和连接表都会影响建连。TCP 只传字节流，不保留应用消息边界；HTTP 的消息帧由上层协议定义。

- Connection refused：地址可达，但端口没有服务接受连接，或被策略拒绝。
- Timeout：在给定时间内未得到响应，可能是路由、防火墙、服务无响应或下游卡住。
- Reset/断开：连接被对端或中间设备关闭，需要比较双方日志。

### Keep-Alive、连接池与 HTTP 多路复用

TCP 和 TLS 建连都有成本。浏览器通常按源维护 HTTP 连接池；后端 HTTP 客户端也会复用到下游服务的连接。Keep-Alive 让多个请求复用连接，减少握手、端口消耗和延迟，但空闲连接仍可能被代理或负载均衡器关闭，因此客户端需要检测失效连接并重新建立。

| 版本 | 连接与并发方式 | 需要知道的边界 |
|---|---|---|
| HTTP/1.1 | 通常通过 Keep-Alive 复用 TCP 连接；浏览器可建立多个并行连接 | 同一连接上的请求/响应顺序限制会影响并发，连接数过多也有资源成本 |
| HTTP/2 | 在一条 TCP 连接上用多个 Stream 多路复用请求 | TCP 丢包仍可能暂时影响该连接上的多个 Stream；并发受客户端和服务器限制 |
| HTTP/3 | 在 QUIC 的多个 Stream 上复用，使用 UDP | 需要客户端、服务端和中间网络支持 QUIC；代理可能终止并转换协议 |

“一个请求一个 TCP 连接”通常不是浏览器与后端的实际工作方式。调试长请求或断连时，要区分浏览器到代理、代理到网关、服务到下游各自的连接池、空闲超时和最大连接数。

连接池需要同时设置最大连接数、获取连接等待上限、空闲回收和连接存活检测。池太小会让并发请求排队；池太大可能耗尽服务端连接、临时端口或下游数据库资源。HTTP 客户端池与 JDBC 连接池是不同的资源池，不能用调大其中一个来修复另一个的等待。

## TLS：保护传输并验证服务身份

TLS 提供传输加密，并让客户端验证服务端证书。证书过期、域名不匹配或证书链不可信会让浏览器在 HTTP 请求前拒绝连接。

TLS 握手会协商协议版本和密码套件，并建立会话密钥；TLS 1.3 通常减少握手往返。客户端通过 SNI 告诉服务器要访问的域名，ALPN 可协商 HTTP/2 或 HTTP/1.1。排查证书错误时检查：

- 浏览器访问的主机名是否在证书 SAN 中；通过 IP 访问时不能假定域名证书会匹配。
- 证书是否过期、系统时间是否准确、证书链是否完整且受信任。
- 代理/CDN 是否终止了 TLS；浏览器到 CDN 是 HTTPS，不代表 CDN 到源站也是 HTTPS。
- 企业代理是否做了 TLS 检查，客户端是否安装并信任相应证书。

不要通过关闭生产证书校验“解决”HTTPS 错误。检查系统时间、访问域名、证书期限和证书链。

## HTTP：接口契约层

HTTP 定义方法、路径、Header、Body 和状态码。前端调试要记录：

- Request URL 和 Method。
- Query 参数或 JSON payload。
- Authorization、Content-Type 等关键 Header。
- HTTP status 与响应体中的业务 code/msg。
- 响应耗时和 Initiator。

GET 查询通常用 URL 参数；POST/PUT 常用 JSON Body。最终以 Controller 参数声明为准。

### 方法、状态码与前端处理

HTTP 方法表达操作意图，但真正行为由服务端契约决定。GET 通常用于读取且应保持安全；PUT 常表示按目标资源整体替换，PATCH 常表示局部修改，POST 常用于创建或执行命令。`GET`、`PUT`、`DELETE` 在协议语义上具有幂等属性约定；具体 API 如果违反约定，要格外检查重试副作用。

| 状态码 | 常见含义 | 前端要确认 |
|---|---|---|
| 200/201/204 | 成功、已创建或无响应体成功 | 业务响应体是否符合约定；204 没有 JSON body |
| 301/302/307/308 | 重定向 | 登录跳转、HTTP→HTTPS、路径变化或跨域跳转 |
| 400/422 | 请求格式或业务参数不合法 | 字段校验信息是否映射到表单 |
| 401/403 | 未认证或无权限 | Token 状态、登录刷新与按钮/接口权限的区别 |
| 404/409 | 资源不存在或状态冲突 | 路径映射、版本冲突、重复提交或资源状态 |
| 429 | 请求被限流 | 重试提示、退避和用户反馈 |
| 500/502/503/504 | 服务内部或代理/下游失败 | 错误来自哪一跳，响应体是否经过统一封装 |

浏览器的 `fetch()` 遇到 404 或 500 时通常仍会兑现 Promise；调用方需要检查 `response.ok` 或状态码，不能把“网络有响应”当成业务成功。Axios 的默认错误处理有所不同，项目的拦截器还可能把 HTTP 错误转换为统一异常。

```js
// 请求订单详情；示例不包含登录 Token，真实项目由统一请求层注入认证信息。
async function loadOrder(orderId) {
  // 对路径参数编码，避免特殊字符改变 URL 结构。
  const safeId = encodeURIComponent(orderId);
  // 发起 GET 请求并声明期望的响应格式。
  const response = await fetch(`/api/orders/${safeId}`, {
    // 通过标准 Header 告诉服务端希望收到 JSON。
    headers: { Accept: 'application/json' },
  });
  // fetch 对 4xx/5xx 仍会返回 Response，因此要显式检查状态。
  if (!response.ok) {
    // 保留 HTTP 状态，供页面或统一错误层区分未登录、无权限和服务错误。
    throw new Error(`HTTP ${response.status}`);
  }
  // 只有确认 HTTP 成功后才解析 JSON 响应体。
  return response.json();
}
```

如果请求返回 204，无响应体可供 `response.json()` 解析；调用方要根据接口契约处理空响应。后端的 HTTP 状态和响应体内业务 code 也可能分层表达错误，两者都要检查。

### 缓存、条件请求与内容编码

`Cache-Control`、`ETag` 和 `Last-Modified` 可以减少重复下载或传输变化部分；静态文件常使用内容哈希做长期缓存，HTML 入口通常需要重新验证。API 是否可缓存要考虑用户身份、租户和权限，不能让共享代理缓存把一个用户的数据返回给另一个用户。`Content-Encoding: gzip/br` 减少文本传输量，但压缩会消耗 CPU，且压缩敏感信息时要评估侧信道风险。

### 长连接：轮询、SSE 与 WebSocket

| 方式 | 通信方向 | 常见场景 | 主要代价 |
|---|---|---|---|
| 短轮询 | 浏览器定时发起 HTTP 请求 | 低频状态刷新、实现简单的管理列表 | 大量空请求和轮询间隔带来的延迟 |
| SSE（Server-Sent Events） | 服务端持续向浏览器单向推送 | 任务进度、通知流、日志事件 | 只支持服务端推送；代理缓冲和空闲超时要配置，断线重连需定义事件 ID |
| WebSocket | 双向持续通信 | 聊天、协同编辑、实时控制 | 需管理连接生命周期、鉴权、心跳、重连、水平扩容和代理 Upgrade 转发 |

WebSocket 初始通过 HTTP Upgrade 建立连接，之后的数据帧不再是普通请求/响应。上线排查要检查负载均衡的空闲超时、心跳间隔、连接数和重连风暴；鉴权续期或权限撤销时，还要定义已有长连接如何失效。SSE 是单向通道，不要把它描述为双向消息系统。

## 代理和网关

正向代理代表客户端向外请求；反向代理代表服务端接收请求再转发到内部服务。Nginx 和 API Gateway 常用于反向代理。

**解决的问题：** 隐藏内部实例、统一 TLS、路由、负载均衡和公共过滤。

**调试代价：** URL 可能被改写，响应头可能被修改，超时可能在多个层分别设置。排查 404、502、504 时要知道错误出现在代理、网关还是业务服务。

代理常用 `Host`、`X-Forwarded-For`、`X-Forwarded-Proto` 等头传递原始请求信息。只有来自受信任代理的转发头才可用于恢复客户端 IP 或外部协议；最外层代理要覆盖不可信的同名头，应用也要配置可信代理边界。否则客户端可以伪造来源地址或让服务误以为外部连接是 HTTPS。

~~~sh
# 在有权限的开发机器上查询域名解析结果。
nslookup api.example.test

# 检查目标 TCP 端口能否建立连接；这不验证业务 URL 是否正确。
nc -vz api.example.test 443

# 请求健康检查响应头；命令不包含任何登录凭据。
curl -I --max-time 10 https://api.example.test/health
~~~

Windows PowerShell 可使用 `Resolve-DnsName api.example.test` 查看解析，并用 `Test-NetConnection api.example.test -Port 443` 检查 TCP 端口连通性；TCP 成功不代表 TLS 证书、HTTP 路由或业务认证正常。

## CORS：浏览器跨源读取控制

同源策略和 CORS 限制网页脚本读取其他源的响应。“源”由协议、主机和端口共同组成。

复杂请求可能先发送 OPTIONS 预检；浏览器根据 Access-Control-Allow-Origin、Methods、Headers 等响应头决定是否发送后续请求，或是否允许页面脚本读取响应。

**关键区别：** CORS 是浏览器跨源访问机制，不是身份认证。请求可能已经执行，但浏览器不让脚本读取结果。用 Network 检查 OPTIONS、实际请求和 CORS 响应头，并查看服务日志。

生产环境不应允许任意来源同时携带凭据；应明确允许的 Origin、方法和 Header。

CORS 预检通常因跨域请求使用非简单方法、非简单 Header 或特定 Content-Type 触发。预检 `OPTIONS` 返回允许策略后，浏览器才会按规则发送实际请求；预检通过也不代表实际请求的认证和业务校验通过。若允许凭据，`Access-Control-Allow-Origin` 不能使用 `*`；服务端还要正确处理 `Vary: Origin`，避免代理缓存混淆不同来源的响应。

## 超时应按链路分层

浏览器、Nginx、Gateway、业务服务、数据库和外部 HTTP client 都可能有自己的超时。链路上较短的上游超时可能先返回错误。

增加浏览器 timeout 不会让后端 SQL 变快。记录每层耗时，区分连接时间、应用处理时间和下游等待时间，再决定应该修 SQL、依赖还是超时配置。

连接超时是建立 TCP/QUIC 或从连接池取连接的等待上限；TLS 握手、响应读取和整条请求 deadline 也可能有独立上限。上游超时后，服务端操作可能仍在运行，所以用户再次点击可能触发并发重复写入；取消请求要结合服务端中断传播和幂等设计验证。

```sh
# verbose 模式输出 DNS、连接、TLS 和 HTTP 阶段的诊断信息；分享输出前先检查是否含 Cookie 或 Token。
curl -v --connect-timeout 3 --max-time 10 https://api.example.test/health

# 查看 TLS 协商、证书链和服务端 ALPN 选择；命令不会验证业务 API 是否正常。
openssl s_client -connect api.example.test:443 -servername api.example.test -alpn h2,http/1.1 </dev/null
```

## 故障表现速查

| 浏览器/HTTP 现象 | 可能位置 | 下一步 |
|---|---|---|
| DNS error | 域名解析 | 检查 DNS、VPN、代理和域名 |
| refused | 目标端口或服务监听 | 检查进程、端口映射、防火墙 |
| CORS error | 浏览器不允许读取跨源响应 | 检查预检、允许来源和响应头 |
| 404 | 代理改写、网关 route 或 Controller 映射 | 对比转发前后路径 |
| 502/503 | 代理无法连接健康上游 | 检查服务注册、实例健康和网络 |
| 504/timeout | 某层超时或下游处理慢 | 关联日志并比较各层耗时 |
| HTTP 200 但业务失败 | 业务响应体 | 检查响应拦截器和异常处理 |

### 从 Network 到服务端的分层排查

1. **确认请求本身：** URL、方法、请求体、请求头、Initiator 和是否由 Service Worker/缓存返回。
2. **看 Timing：** DNS、建连、TLS、等待首字节和下载分别耗时多少；浏览器是否复用连接。
3. **看浏览器错误：** CORS、证书、mixed content、blocked by client 与 HTTP 状态码是不同类型问题。
4. **核对入口转发：** 根据 requestId 在 CDN/Nginx/Gateway 日志里确认外部路径如何改写，以及请求是否到达业务实例。
5. **关联应用日志：** 用 traceId 查 Controller、远程调用和数据库耗时；没有服务端日志时不能只靠浏览器判断后端原因。
6. **复测并固定条件：** 对比同一账号、同一环境和相同数据的成功/失败请求，避免把权限、缓存或数据差异误认为网络故障。

## 练习

用 Network 记录一次成功与一次失败请求，观察使用的 HTTP 版本、连接复用和耗时。将失败定位到 DNS、TCP/QUIC、TLS、代理、HTTP 或业务响应某一层，并用可观察证据说明判断过程。
